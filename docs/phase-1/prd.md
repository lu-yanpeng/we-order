# PRD: We-Order 点餐小程序 — Phase 1: 静态页面与交互

## 0. 文档说明

本 PRD 为 We-Order 项目**四阶段开发计划中的第一阶段**，聚焦于小程序端的静态页面开发与前端交互实现。所有数据使用本地 Mock，不依赖任何后端服务。

**四阶段开发计划：**

| 阶段 | 范围 | 目标 |
|------|------|------|
| **Phase 1**（本文档） | 小程序静态页面 | 1:1 还原 HTML 原型，Mock 数据驱动全部交互 |
| Phase 2 | Supabase 后端开发 | 数据库设计、接口开发、Edge Functions |
| Phase 3 | 小程序对接 Supabase | 替换 Mock 为真实 API，跑通 MVP 闭环 |
| Phase 4 | B 端后台管理系统 | 基于 Vben Admin 的运营后台 |

**技术栈：** Uniapp + Vue + TypeScript + TailwindCSS。

本文档面向开发者 Ly，以已有的 HTML 原型（Open Design 设计产物）作为 UI/UX 唯一参考基准。PRD 不重复描述视觉细节，所有页面布局以原型为准。

## 1. 愿景

We-Order 是一款借鉴星巴克 UI 设计规范的原创点餐微信小程序，作为开发者 Ly 的前端工程能力名片——向面试官和技术主管证明候选人能独立完成一个有完整业务闭环的复杂前端项目。

**Phase 1 的目标：** 以本地 Mock 数据驱动，1:1 还原 HTML 原型的所有页面和交互，确保每个页面都能独立运行并展示完整的 UI 效果。

## 2. 目标用户与关键旅程

**目标受众：** 技术面试官、前端技术主管。Phase 1 的交付物是一套可运行、可演示的静态小程序页面。
Phase 1 有意仅设一条主线演示旅程（供面试展示），后续阶段将扩展旅程覆盖。

### UJ-1: Ly 在面试现场演示完整的点餐流程

> 打开小程序后直接进入点餐页（Phase 1 无需登录）。在左侧分类栏点击「经典咖啡」，右侧商品列表平滑滚动到对应区域。点击美式咖啡的 `+` 按钮，底部弹出商品定制面板，选择大杯/冰/燕麦奶/1份浓缩，点击「加入购物袋」。底部结算栏动态加载并滑入，显示合计金额。点击「结算」跳转到确认订单页，选择「打包外带」，包装费自动加 ¥2，填写备注「少冰」，点击「立即支付」。前端模拟支付成功后，页面跳转到订单列表，展示不同状态的订单卡片（制作中/待取餐/已完成）。面试官看到了一个完整的交互闭环。

## 3. 术语表

| 术语 | 定义 |
|------|------|
| **商品 (Product)** | 菜单中可供选择的饮品或食品条目。Phase 1 使用本地 Mock 数据。 |
| **分类 (Category)** | 商品的归属类别，如「今日推荐」「经典咖啡」等。一个商品属于且仅属于一个分类。 |
| **规格 (Specs)** | 商品的可定制维度：杯型、温度、牛奶、加料、浓缩份数。每项规格可能影响最终价格。 |
| **SKU** | 商品 + 规格组合的唯一标识。SKU 完全相同 = 同一商品 + 完全相同的规格选择。 |
| **购物车 (Cart)** | 用户已选商品及规格的本地暂存集合。仅保存在前端本地存储中，清除缓存后消失。`[ASSUMPTION: 仅保存在前端本地存储中，清除缓存后消失。]` |
| **结算栏 (Checkout Bar)** | 贴底浮动组件，展示合计金额和结算入口。作为分包组件按需动态加载。 |
| **订单 (Order)** | Phase 1 中由前端本地创建的模拟业务实体。 |
| **订单状态 (Order Status)** | 生命周期阶段：`制作中 → 待取餐 → 已完成`。Phase 1 通过 Mock 数据展示 UI。 |
| **取杯号 (Pickup Code)** | 订单进入「待取餐」状态后的短编号（如 A-08）。Phase 1 为 Mock 数据。 |
| **就餐方式 (Dining Mode)** | 「店内堂食」或「打包外带」。外带额外收取 ¥2 包装费。 |

## 4. 功能需求

### 4.1 商品浏览与分类导航

**描述：** 点餐页采用双栏联动布局——左侧分类导航栏，右侧商品列表。双向滚动联动，分类标题 sticky 吸顶。商品数据从本地 Mock 加载。实现 UJ-1。

#### FR-1: 分类导航与商品列表联动

用户可在左侧分类栏中点击任意分类，右侧商品列表平滑滚动到该分类区域。

**验收条件：**
- 点击左侧分类后，右侧对应分类区块滚动到可视区域顶部。
- 右侧自由滚动时，左侧当前分类自动高亮。
- 分类标题在滚动时保持吸顶。

#### FR-2: 商品卡片展示

每个商品卡片展示商品图片、名称、描述、月销量、标签（如「人气新品」「今日热销」）和基础价格。

**验收条件：**
- 商品数据从本地 Mock JSON 加载。
- 卡片布局与 HTML 原型保持一致。

### 4.2 商品定制

**描述：** 点击商品卡片的 `+` 按钮后，底部弹出定制面板（Bottom Sheet），可选择规格，价格实时联动。实现 UJ-1。

#### FR-3: 规格选择与价格实时计算

用户在定制面板中选择杯型（中杯 / 大杯 / 超大杯）、温度（冰 / 热）、牛奶（燕麦奶 / 全脂牛奶 / 椰乳）、加料（焦糖淋酱 / 稀奶油 / 可可碎片，可多选）、浓缩份数（步进器，最少 1 份）。

**验收条件：**
- 选项变更后，面板底部的价格和规格摘要文本实时更新。
- 价格计算规则：基础价格 + 杯型差价 + 牛奶差价 + 加料总价 + 额外浓缩费用。`[ASSUMPTION: Grande +¥3, Venti +¥6; 燕麦奶/椰乳 +¥2; 每多一份浓缩 +¥4; 焦糖淋酱 +¥3, 稀奶油 +¥4, 可可碎片 +¥4]`
- 默认选项：大杯 / 冰 / 燕麦奶 / 1 份浓缩 / 无加料。
- 规格选项从本地 Mock 数据加载。

#### FR-4: 加入购物袋

用户点击「加入购物袋」后，商品及其规格被添加到购物车。

**验收条件：**
- SKU 完全相同的商品自动合并数量。
- 添加成功后定制面板自动关闭。
- 结算栏同步更新合计金额和商品数量。

### 4.3 购物车与结算栏

**描述：** 结算栏为分包组件，按需动态加载。购物车状态仅保存在前端本地存储中，清除缓存后数据消失。实现 UJ-1。

#### FR-5: 结算栏分包动态加载

加载策略：（a）进入应用时，若购物车已有商品则立即加载；（b）若购物车为空，首次加购时触发加载；（c）一旦加载，永久可见，不销毁不隐藏。

**验收条件：**
- 首次进入且购物车为空时，结算栏不渲染（DOM 中不存在）。
- 首次加购后，结算栏从底部滑入并显示。
- 清空购物车后，结算栏仍然可见（显示 ¥0 / 结算(0)）。`[ASSUMPTION: 清空后结算栏显示零状态]`

#### FR-6: 购物车抽屉

用户点击结算栏的「明细」区域后，从底部弹出购物车抽屉，显示已购商品列表（名称、规格、价格、数量步进器）。

**验收条件：**
- 步进器可增减商品数量，减至 0 时自动移除该商品。
- 「清空购物袋」按钮一键清空所有商品。
- 抽屉关闭后结算栏金额同步更新。

### 4.4 确认订单

**描述：** 用户点击结算栏的「结算」按钮后，跳转到独立的确认订单页面（独立 page，navigateTo 跳转，非覆盖层）。展示就餐方式、门店信息（Mock 固定数据）、商品明细、费用汇总、备注偏好。实现 UJ-1。

#### FR-7: 就餐方式切换

用户可以在「店内堂食」和「打包外带」之间切换。

**验收条件：**
- 默认为「店内堂食」。
- 切换为「打包外带」时，自动增加 ¥2 包装费，费用汇总和应付金额实时更新。
- 取餐时间 ETA：堂食显示「预计 10-15 分钟后可取」，外带显示「预计 15-20 分钟后打包完成」。`[ASSUMPTION: ETA 文案固定，不做动态计算]`

#### FR-8: 备注偏好输入

用户可输入特殊偏好（如「少冰」「不要餐具」）。

**验收条件：**
- 默认显示「无备注要求」。
- 备注内容随订单一并保存到本地订单记录。

#### FR-9: 确认订单页信息展示

完整展示：门店名称和地址（Mock 固定数据）、商品明细（名称、规格、数量、单价）、包装费（外带时显示）、商品总数与实付金额、支付方式（固定显示「微信支付」）。

**验收条件：**
- 所有数据与购物车状态和就餐方式选择保持一致。
- 页面布局与 HTML 原型保持一致。

### 4.5 模拟支付

**描述：** 用户点击「立即支付」后，前端模拟支付成功。不对接任何后端或真实支付通道。Phase 1 为纯前端延迟模拟。实现 UJ-1。

#### FR-10: 前端模拟支付流程

用户点击「立即支付」后，前端展示 loading 状态，短暂延迟后显示支付成功反馈，清空购物车、重置备注和就餐方式，在本地创建订单记录，跳转到订单列表页。

**验收条件：**
- 支付过程展示 loading 状态（如 Spinner），模拟 1-2 秒延迟后展示成功反馈。`[ASSUMPTION: 模拟支付为纯前端延迟模拟（1-2 秒），不调用后端。]`
- 成功后自动清空购物车，跳转到订单列表页。
- 新订单保存在本地存储中，显示在列表顶部，状态为「制作中」。

### 4.6 订单历史与状态展示

**描述：** 订单页展示所有本地订单记录。Phase 1 使用预置 Mock 数据展示不同状态的订单卡片 UI 效果。实现 UJ-1。

#### FR-11: 订单列表展示

订单页按时间倒序展示所有订单卡片，每个卡片包含：订单编号、状态标签（制作中/待取餐/已完成，颜色区分）、就餐方式、商品名称与规格摘要、备注、金额。

**验收条件：**
- 状态标签颜色：制作中（蓝色）、待取餐（金色）、已完成（绿色）。
- 本地存储中预置至少 3 条不同状态的 Mock 订单，用于 UI 展示。
- 用户模拟下单后创建的新订单追加到列表顶部。

#### FR-12: 订单状态 UI 展示

Phase 1 不实现真实的状态流转逻辑。通过预置 Mock 数据展示三种状态的 UI 差异。

**验收条件：**
- 「制作中」状态的订单显示进度指示和「催单」按钮（点击后显示轻提示「已通知门店加快制作」，无后端逻辑）。`[ASSUMPTION: 催单仅触发前端轻提示]`
- 「待取餐」状态的订单显示取杯号和「确认取杯」按钮。
- 「已完成」状态的订单显示「再来一单」按钮。

### 4.7 订单详情

**描述：** 用户点击订单卡片后，跳转到独立的订单详情页面（独立 page，navigateTo 跳转）。根据订单状态展示不同的顶部状态卡片。实现 UJ-1。

#### FR-13: 订单详情页

根据当前订单状态展示对应的顶部状态卡片：
- **制作中**：显示进度指示和预计完成时间。
- **待取餐**：显示取杯号、模拟条形码和「确认取餐」按钮。
- **已完成**：显示完成提示和「再来一单」按钮。

同时展示：门店信息（Mock 固定数据：名称、地址、电话、堂食/外带标签）、商品明细（含包装费）、订单编号、下单时间、支付方式、备注偏好。

**验收条件：**
- 详情页数据与订单列表保持一致。
- 状态卡片的交互（确认取餐、再来一单）功能正常。
- 页面布局与 HTML 原型保持一致。

### 4.8 再来一单

**描述：** 用户在已完成订单中点击「再来一单」，系统将原订单所有商品合并到当前购物车，然后跳转到确认订单页。实现 UJ-1。

#### FR-14: 再来一单

用户点击「再来一单」后，系统将原订单中的所有商品（保留完整规格和数量）合并到当前购物车，然后跳转到确认订单页。

**验收条件：**
- **合并规则：** 对于再来一单中的每个商品，若购物车中已存在 SKU 完全相同的商品，则用再来一单的数量**覆盖**购物车中的数量（不累加，避免用户因重复操作导致购物车数量意外翻倍）。购物车中其他不相关商品保持不变。
- **不可用商品处理：** 当商品下架、规格不可用、或库存不足（如原订单数量为 2 但库存仅剩 1）时，该商品不加入购物车，并通过轻提示（Toast）通知用户具体原因。`[ASSUMPTION: Phase 1 Mock 数据下所有商品均可用，此校验逻辑在 Phase 3 对接后端后实现]`
- 跳转到确认订单页后，用户可直接支付，也可返回修改购物车。

## 5. 明确的非目标

- **不做**任何后端服务对接——Phase 1 全部使用本地 Mock 数据。
- **不做**微信登录/授权——Phase 1 直接进入应用，无需登录。
- **不做**真实的订单状态流转——通过预置 Mock 数据展示 UI。
- **不做**真实支付——纯前端延迟模拟。
- **不做** B 端后台管理系统。
- **不做**用户个人中心（积分、卡券、手机号绑定）。
- **不做**搜索功能。
- **不做**门店切换或定位——使用固定的 Mock 门店信息。`[ASSUMPTION: MVP 使用固定的模拟门店信息]`
- **不做**优惠券、折扣、满减等营销功能。
- **不做**商品 SKU 的后端动态配置——规格选项 Phase 1 中使用 Mock 数据。

## 6. Phase 1 范围

### 6.1 包含

- 商品浏览：分类导航与商品列表双栏联动、分类吸顶。
- 商品定制：杯型、温度、牛奶、加料（多选）、浓缩份数，实时价格计算。
- 购物车管理：加购、改数量、移除、清空。本地存储，清除缓存后消失。
- 结算栏：分包组件按需加载策略。
- 确认订单：就餐方式切换（堂食/外带 + 包装费联动）、商品明细、备注、前端模拟支付。
- 订单列表：不同状态 Mock 数据的 UI 展示（制作中/待取餐/已完成）。
- 订单详情：状态卡片、Mock 门店信息、商品明细、订单元信息。
- 再来一单：合并商品到购物车并跳转确认页。
- 完整的本地 Mock 数据集。

### 6.2 不包含

- 任何后端服务调用（Supabase、微信授权等）。
- 真实的订单状态流转逻辑。
- 商品 SKU 后端动态配置。
- B 端后台管理系统。
- 用户个人中心、搜索、多门店切换、营销功能。

## 7. 成功指标

本项目的受众是面试官而非真实用户，因此不设定传统的 DAU / 留存 / 转化指标。

| 指标 | 描述 | 目标 | 验证范围 |
|------|------|------|---------|
| **SM-1** | 完整交互流程跑通率——从进入应用到模拟支付成功到订单展示，全流程无阻断 | 100% | FR-1 至 FR-14 |
| **SM-2** | 原型还原度——UI 表现与 HTML 原型高度一致（开发者自评） | ≥ 90% | FR-2, FR-9, FR-13 |

**反指标：** 不以功能数量衡量进度——宁可少做功能但每个做到位，也不为了数量牺牲还原度和交互质量。
