# We-Order 点餐小程序 · Phase 2（Supabase 后端）— Epic 分解

## Overview

本文档把 We-Order Phase 2 的需求（PRD 的 FR-P2-1 ~ FR-P2-19 与跨切面 NFR、架构 spine 的 AD-1 ~ AD-24 与继承不变量）分解为可实施的 Epic 与 Story。

Phase 2 的产品形态：**小程序界面零变化**，改动集中在服务端（Supabase）与小程序登录链路。本阶段不新增面向顾客的功能，交付物是「真实后端 + 归属隔离 + 可复现重建 + 测试证明」。

输入文档说明：UX 设计契约**不存在**，理由见下方「UX 设计需求」一节。Phase 1 的 PRD 与架构 spine（`_docs/phase-1/`）是界面与前端行为的基准，按其约定不在本次输入清单内，仅在需要追溯时引用。

## Requirements Inventory

### Functional Requirements

FR-P2-1 微信登录换取身份：小程序用微信下发的一次性凭证换取 OpenID；凭证只能消费一次；换取只在服务端发生，AppSecret 不出现在小程序包、客户端源码或客户端可读配置中；换取失败按原因分类（AppID 无效 / 密钥无效 / 凭证无效 / 凭证过期或已用 / 高风险用户被拦截 / 频率超限），不做成统一的「登录失败」；全过程无用户交互、无授权弹窗、不请求任何用户资料。

FR-P2-2 身份映射与用户建立：同一 OpenID 重复登录得到同一个用户，不同 OpenID 得到不同用户；同一 OpenID 的并发首次登录只产生一个用户；已建立的映射不可被另一个 OpenID 复用。

FR-P2-3 会话签发：登录成功后签发一套可续期会话（访问凭证 + 刷新凭证）；凭会话即可访问受数据访问策略保护的数据，无需额外凭证；会话主体与 OpenID 映射到的用户一致；会话使用平台标准签发机制，不使用自签 JWT。

FR-P2-4 会话持久化与自动续期：会话凭证持久化在客户端本地存储、应用重启后可恢复，无需用户再次操作；访问凭证过期后再次发起任一受保护请求仍返回成功——续期对调用方透明，不出现「先失败再重试」；续期不可用时回退为重新静默登录，且不会产生第二个身份。

FR-P2-5 登录失败的可见反馈：「网络不可达」「微信侧限流」「凭证失效」三类对应三个不同的错误类别与不同文案；提示与日志中都不包含 AppSecret、服务端密钥、内部堆栈或数据库细节；失败后可重试，重试不留下半登录状态（不产生孤儿用户、不残留不可用会话）。

FR-P2-6 分类与商品读取：未登录可读取分类、商品、规格组与规格选项；返回字段以后端列名为准（snake_case），字段集合与 Phase 1 的 `Category` / `Product` / `SpecGroup` / `SpecOption` 语义一一对应；商品具备三态可售状态，下架商品不出现在结果中、售罄商品保留并返回状态、分类下没有任何「非下架」商品时该分类不返回；`sales` 为种子数据中的静态展示值，不随订单聚合；保留规格组的「多选」语义；规格选项加价金额同时是展示来源与计价来源（不存在两套价格）；未登录请求不被拒绝。

FR-P2-7 商品图片读取：图片由对象存储提供、未登录可读；存储桶与读取策略、图片对象以声明式方式入仓，不依赖控制台手工操作；商品记录中的图片引用与存储中的对象一致（重建后不存在「引用存在但对象缺失」）；图片缺失或加载失败不阻塞商品列表渲染；图片上传路径不在本阶段。

FR-P2-8 门店读取：门店名称、地址、电话由一个查询得到，系统中不存在第二处门店数据来源；提交订单时记录门店引用与门店快照（名称、地址、电话）；不提供门店列表、切换或定位能力。

FR-P2-9 提交订单与金额重算：订单与明细不向客户端开放直接写入权限，下单只能经由服务端函数；归属取自会话身份，客户端传入的任何用户标识被忽略；客户端提交内容只含商品引用、规格选择、数量、就餐方式、备注（不含金额）；逐行单价与总额由服务端按库内价格规则重算（基础价 + 规格加价；外带包装费 2.00 元、堂食 0 元；单位元、保留两位小数）；非法输入整单拒绝且不留任何数据；订单与明细在同一事务内写入；订单快照完整（商品名、规格选择结构化副本、服务端生成的规格摘要、单价、数量），商品改名改价不影响历史订单；订单号由服务端生成（`SG` + 8 位数字）且全局唯一；备注未传或为空落库为「无备注要求」；新订单初始状态「制作中」、取杯号为空、写入推进时刻，创建时间取服务端时钟；时间以带时区时间戳存储、对外按 `YYYY-MM-DD HH:mm:ss`（门店本地时区）输出。

FR-P2-10 重复提交防护：客户端提交携带必填幂等标识；同一标识的重复提交返回同一张订单且不重复写入；幂等标识与用户绑定，其他用户携带该标识只会得到属于自己的新订单或明确拒绝，绝不取回他人订单；不同标识的两次提交产生两张订单；并发情况下同样只落一张订单。

FR-P2-11 状态推进与取杯号生成：订单在固定时长（默认下单后 15 秒，可配置）后进入「待取餐」并分配取杯号；判定与执行都在服务端（读取时判定 + 周期兜底扫描），客户端不参与判定、不能传参改变推进时刻或状态；取杯号在门店本地时区的同一自然日内唯一、跨日可重复，外形为字母前缀 + 两位数字（如 `A-08`）；推进与用户操作并发时最终状态唯一、取杯号不重复；推进过程幂等（不产生第二个取杯号、不跳状态）；只接受合法迁移（制作中→待取餐→已完成），非法迁移被拒且不改变当前状态；推进任务失败后可安全重跑。

FR-P2-12 催单加速：已登录用户可对本人处于「制作中」的订单催单，把推进时刻提前到「当前时刻 + 3 秒」（可配置）；催单只提前推进时刻，状态变更仍由推进机制完成；推进时刻取「原定时刻」与「催单时刻 + 提前量」的较早者，该更新是原子的、与推进并发时不会导致推进被延后或丢失；重复催单不会更早也不会更晚；对非本人订单拒绝且不泄露该订单是否存在；对本人但状态已非「制作中」的订单返回明确的「当前状态不可催单」结果。

FR-P2-13 确认取杯：已登录用户可把本人处于「待取餐」的订单置为「已完成」；其他状态返回明确拒绝结果；重复确认幂等（不报错、不改变状态、不修改完成时间）；与推进并发时结果确定（要么基于更新后的状态成功完成，要么返回明确的「状态已变化」，不产生中间态）；不需要额外凭证（不做取餐码核销）。

FR-P2-14 我的订单列表：已登录用户可分页读取自己的订单，按创建时间倒序；结果只含本人订单；分页边界稳定（翻页过程中不重复、不遗漏已存在订单），默认每页 20 条；返回结构与 Phase 1 的 `Order` 兼容且字段齐备（订单号、状态、就餐方式、商品摘要、金额与包装费、备注、取杯号、创建时间）；未登录请求被拒绝，而不是返回空列表。

FR-P2-15 订单详情：已登录用户可读取本人订单的完整信息；只能读取本人订单，访问他人订单标识时被拒绝且拒绝方式不泄露该订单是否存在；详情包含商品明细（含快照与数量）、门店信息（名称、地址、电话）、订单号、下单时间、就餐方式、备注与金额；详情与列表读取自同一数据源，不存在两套口径。

FR-P2-16 迁移与种子数据（可复现重建）：全部结构变更以迁移文件形式存在；种子数据覆盖目录类数据（分类、商品含可售状态、规格组与选项、门店、商品图片引用）且不包含订单；对象存储的桶与读取策略、图片对象同样以声明式方式入仓；在干净环境上从零重建出与云端一致的结构、目录数据与图片不需要任何手工步骤；重建后的数据库可立即用于登录、下单与订单查询。

FR-P2-17 类型契约：类型可从当前数据库结构生成且生成物入仓，重新生成不需要任何手工修改；结构变更后重新生成即可反映变化；服务端返回的字段与生成类型一致（含可空性）；对快照类字段（规格选择、门店快照等 JSON 结构）明确标注为需要手工类型覆盖；不承诺客户端的编译期保护（属 Phase 3 验收）。

FR-P2-18 数据访问策略（RLS）：所有对外暴露的表启用行级访问控制且默认拒绝未授权访问；目录类数据允许公开读取，订单与订单明细只允许本人读取；已登录用户没有订单与明细的直接写入授权，写入只能经由服务端函数；未认证请求无法读取任何订单数据；拥有绕过策略权限的服务端密钥不出现在客户端；拿到发布密钥直接访问数据库者读不到他人订单、也无法自行写入一张金额自定的订单。

FR-P2-19 后端测试基线：测试覆盖三类边界（他人数据不可见、他人数据不可写、未认证不可读）；覆盖关键业务函数（下单金额以重算结果为准、归属取自会话、非法状态迁移被拒、推进重复执行幂等）；测试可在本地以一条命令运行且失败时能定位到具体策略或函数；测试在重建后的空库上可直接运行通过；并发行为与真机链路不在数据库层测试范围内，以「实现方式说明 + 人工验证记录」作为证据。

### NonFunctional Requirements

NFR1 性能：读取类请求（目录、订单列表、订单详情）的服务端处理时间目标为数百毫秒内（以本地与云端免费实例实测为准，本阶段不设 SLA 数值）；订单列表分页默认 20 条，避免一次拉全量；不出现随数据增长线性变慢的实现（例如无分页的全表扫描）；任何列表类读取都不得返回无界结果集，分页参数有上限。

NFR2 可靠性：任何写操作失败都不得留下中间态（订单与明细同事务、状态迁移以原子更新完成）；推进机制的一次失败不应导致订单永久卡在「制作中」——读取时的判定与周期性兜底共同保证；推进任务必须短小、幂等、可重跑。

NFR3 可观测性：错误必须可区分、可定位——登录失败、下单校验失败、状态迁移被拒各自对应明确的错误类别枚举，而不是统一的「服务器错误」；关键失败（登录换取失败、下单被拒、推进异常）在服务端留下带错误类别与请求标识的记录；日志中不得出现 AppSecret 或服务端密钥。

NFR4 安全基线：最小权限原则；客户端只持有发布密钥；服务端密钥仅存在于服务端运行环境；传输全部走 HTTPS。

NFR5 兼容性：以后端生成的类型为唯一形状基准；Phase 3 的对接方式是让前端类型向生成类型对齐，而不是要求后端迁就 Phase 1 手工定义的类型；对接期允许加法型改动（新增字段、可选参数、补查询），不允许结构性返工（重做数据模型、重写接口契约形状、改动数据归属关系）。

### Additional Requirements

来源：架构 spine（AD-1 ~ AD-24、Inherited Invariants、Consistency Conventions、Stack、Structural Seed）与 PRD §6 平台约束。

**仓库边界与起点**

- AR-1 无 starter 模板：架构未指定任何 greenfield/starter 模板。本仓库为**规划仓库**，只产出 PRD、架构与 Epic 文档；实际实现发生在**开发仓库 `we-order`**（含 `mp/` 与 `supabase/`）。Epic 1 的第一个 story 不是「从模板初始化项目」，而是「在既有开发仓库内建立 Supabase 项目骨架」。
- AR-2 开发仓库的 Supabase 目录契约：`supabase/config.toml`（本地栈配置；桶与图片对象声明 `objects_path`）、`supabase/migrations/`（全部结构变更：表、策略、函数、桶策略、`cron.schedule`）、`supabase/seed.sql`（目录种子数据，不含订单）、`supabase/functions/wechat-login/`（唯一边缘函数：code2Session → find-or-create → 签发会话）、`supabase/tests/`（pgTAP）。
- AR-3 环境与拓扑：本地 Docker 容器（迁移 + 种子 + 桶 + 图片，pgTAP 测试）与云端单一托管实例（Postgres 17、Storage 公开读桶、Edge Function `wechat-login`、Cron 兜底推进）；两边由同一批声明重建/推送，结构一致性以迁移列表一致为证据。
- AR-4 技术栈与版本：Postgres 17（本地容器同一大版本）、Supabase CLI（跟随最新）、Deno 兼容边缘函数运行时、Supabase Cron（pg_cron，支持 30 秒级周期）、Supabase Storage、pgTAP（经 `supabase test db`）、客户端手写 `wx.request`（不引 supabase-js 与社区适配库）、`supabase gen types typescript`、Docker。

**安全、密钥与配置**

- AR-5 密钥边界与会话签发：客户端只允许出现发布密钥；AppSecret 与平台密钥只存在于服务端运行环境；客户端请求恒带 `apikey: <发布密钥>`，需要身份的请求附 `Authorization: Bearer <访问凭证>`，发布密钥不是 JWT、不得放入 `Authorization`；会话一律由平台签发，禁止自签 JWT；登录边缘函数被调用时尚无会话，须关闭平台前置 JWT 校验并在函数内自行校验输入；边缘函数密钥经平台 secret 注入且密钥名不能以 `SUPABASE_` 开头；仓库内不出现任何密钥，`.env` 不入仓。
- AR-6 结构与配置声明式入仓纪律：全部结构变更以迁移文件存在；桶、图片对象、定时任务均声明式入仓，不属于「可以手工补」的范围；任何「只在控制台点过」的结构视为不存在；结构只允许经迁移变更以保证本地与云端一致；使用 `migration squash` 前须知它**会丢弃 cron 任务与桶**。

**类型与测试**

- AR-7 类型契约工程化：类型由数据库结构生成，生成物入仓且只有一份，小程序与边缘函数引用同一份，不手工编辑生成物；快照类 JSON 字段标注为需手工类型覆盖，不假装生成类型能给出精确形状；服务端函数的返回形状属于契约而非实现细节，由数据库类型定义（见 AR-17）。
- AR-8 测试工程化：测试用 pgTAP，以 `supabase test db` 一条命令运行，不引入第三方 helper；模拟身份使用平台当前的 claim 注入方式——**写法本身不写入契约，以实现时的官方文档为准，契约是测试结果**；测试必须能在重建后的空库上直接通过。

**客户端范围与继承不变量**

- AR-9 客户端 Phase 2 范围与落点（AD-14 / AD-15）：小程序侧只接登录链路（取一次性凭证 → 换取会话 → 本地持久化）与一个最小验证入口；目录与订单继续读 Mock，不为 Phase 3 预建正式对接层；会话的持有、持久化、过期判断、续期与失败回退全部封在 `api/auth/` 内，对 composable 与页面不可见（判据：上层代码不出现 token 一词，请求头构造也只在 `api/` 内）；`api/` 不向上层暴露「未登录」状态；登录为惰性；**续期实现必须单飞**（同一时刻只允许一个续期在飞，其余请求等待并复用结果）；本地存储 key 沿用 `weorder_` 前缀，会话为 `weorder_session`。
- AR-10 继承的代码组织不变量（Phase 1 AD-1/AD-2/AD-3/AD-7/AD-9、Pinia 约定、命名与文件组织）：数据流为 `页面 → Composable`，外部数据读写必须经 `api/`；模块依赖方向 `pages/ → composables/ → api/`，下层不得引入上层；页面只做编排、业务逻辑在 Composable；不建全局错误拦截器（全局错误处理属 Phase 3）；composable 先放使用它的包内；会话不进 Pinia，本阶段不新增、不改动 store；kebab-case、组件目录 `index.vue`、SFC 区块顺序。
- AR-11 已记录的偏离（有期限例外，评审时不得当作违规）：Phase 1 AD-1 含「API 层不持有运行时状态」，而 AD-14 让会话凭证与续期状态住在 `api/` 内。ly 已裁示接受，Phase 3 正式对接时一并修正。

**数据库层机制落点**

- AR-12 归属表达点与 RPC 权限模型（AD-3 / AD-5）：归属只在服务端表达，且表达点恰好两处、必须同构——**读**由 RLS 策略表达（`orders` 只允许本人 SELECT），**RPC 内部**由谓词表达（等价于 `user_id = (select auth.uid())`）；客户端永远不是归属的表达点；两处谓词的等价性由测试钉住（同一身份经 RPC 与经裸表读取，可见行集合必须相同）。面向用户态写操作的 RPC（下单、催单、确认取杯、订单读取）一律 `SECURITY DEFINER` 且设置 `search_path = ''`，自身携带归属谓词，不附带任何额外表权限；订单列表与详情经服务端函数读取，函数内先推进调用者到点的订单再返回；`orders` 的本人 SELECT 策略保留作纵深防御。
- AR-13 状态迁移机制与触发策略分离（AD-6）：`orders.status` 的写入只存在于一处实现（推进函数），合法迁移只有 `cooking→pickup`、`pickup→completed` 两条；一切对 `orders` 的写都是带状态谓词的原子更新（含催单对 `ready_at` 的写入），不得先读后写；「何时该推进」来自同一处配置，不写死在判断里；读时推进只作用于调用者自己到点的订单，周期兜底作用于全部到点订单，两者调用同一实现；一切时间判定使用服务端时钟（数据库 `now()`）；推进函数不绑定归属以便 Phase 4 由商家触发，且不向客户端暴露。
- AR-14 取杯号分配（AD-7）：唯一域为「门店 + 门店本地自然日」，由该域上的唯一约束保证；取号与状态迁移由同一条语句完成（计数器 `insert ... on conflict do update ... returning`），**允许跳号，不允许重号**；不用「查最大值加一」。
- AR-15 价格、快照与时间（AD-8 / AD-9 / AD-10）：价格只有两个定义点（`products.price`、`spec_options.price_extra`），同时服务展示与重算；加价规则实现为无表访问的纯计算函数；金额列用 `numeric(10,2)`，精度由数据库类型保证、不依赖客户端计算；`order_items` 保存下单时刻副本（商品引用、商品名、规格选择、规格摘要、单价、数量），订单另存门店快照（名称、地址、电话）；订单读取只读副本字段，不 join 目录表取当前值；时间以 `timestamptz` 存绝对时刻，`stores.timezone` 是唯一时区来源，供对外格式化与取杯号自然日切分共用，对外格式化只有一个实现且列表与详情共用。
- AR-16 幂等与有界读取（AD-11 / AD-23）：幂等标识由客户端生成且必填，是 `orders` 上的列，唯一域为 `(user_id, idempotency_key)`，并发重复提交由该约束兜住而非先查后插，不另建幂等表；订单列表必须分页，默认每页 20 条，排序为创建时间倒序且稳定，分页参数有上限。
- AR-17 共享形状只有一处定义（AD-22）：规格选择形状为 `规格组 id → 选项 id 或选项 id 数组`（数组仅出现在多选组），写入快照与「再来一单」读回使用同一形状；订单对外形状（列表与详情的字段名、空值规则——未分配取杯号为空值而非空串、时间与金额格式）由同一映射产出；分页信封语义与默认值只有一处定义；错误以 AD-12 的类别值随平台标准错误载荷返回，不自定义第二套错误信封。
- AR-18 身份映射边界（AD-24）：身份映射表只做 `openid ↔ 平台用户`；`openid` 上有唯一约束，并发首登由该约束收敛为同一用户；映射一旦建立不得被另一个 `openid` 复用；除 `openid` 与时间戳（建立时间、最近登录时间）外不存任何个人信息；不另建用户表——用户即平台用户；`wechat_identities` 与 `pickup_code_counters` 属内部表，不携带任何面向客户端的策略。

**运行约束与约定**

- AR-19 平台约束对实现的要求：边缘函数有内存与运行时长上限、无持久化磁盘、冷启动数百毫秒，不能依赖本地文件状态、不做长任务；调度**不支持「事件发生后延时 N 秒执行一次」**，推进只能采用「读取时判定 + 周期兜底」；免费版实例空闲会被暂停；迁移的本地全量重建与数据库层测试依赖本机 Docker；周期任务的并发与单次时长有限，推进逻辑必须短小、幂等、可重跑；微信侧换取 OpenID 的接口不需要 IP 白名单但有频率限制；AppSecret 只在生成时显示一次。另：小程序可请求域名必须 ICP 备案，Supabase 域名无法加入白名单，开发期依赖三条绕过手段（开发者工具不校验 → 真机/体验版打开调试 → 同一局域网 IP 直连），正式发布链路不在本阶段。
- AR-20 命名、枚举与可观测性约定：表名小写复数下划线（`order_items`），函数动词开头（`create_order`、`advance_due_orders`），枚举值小写下划线（`cooking`）；订单状态 `cooking`/`pickup`/`completed`，就餐方式 `dinein`/`takeout`，可售状态三态：下架不出现在目录读取结果中，售罄保留并随结果返回状态；订单号 `SG` + 8 位数字（唯一约束 + 冲突重试）；取杯号未进入「待取餐」时为空值；备注未传或为空一律落库为「无备注要求」；错误类别是字符串枚举、定义在数据库类型中并随类型契约生成到客户端，微信错误码到类别的映射只存在于边缘函数，客户端只有一个翻译函数，**类别的取值集合以数据库中的定义为唯一来源**，类别是稳定契约、文案不是；服务端日志带错误类别与请求标识。

## Epic 2: 静默登录与可续期会话

用户打开小程序即静默获得身份，重启后仍是同一身份；凭证过期对调用方透明，续期不可用则回退重新静默登录且不产生第二个身份；失败按原因区分且不泄露内部细节；真机一次通过。

### Story 2.1: 边缘函数换取 OpenID 与错误分类

As a 小程序用户，

**Acceptance Criteria:**

**And** 换取只在服务端发生；AppSecret 只来自服务端运行环境（平台 secret，名称不以 `SUPABASE_` 开头），小程序包、客户端源码与客户端可读配置中均不存在

**And** 其中可构造的四类（前四类）可用受控输入注入并断言分类正确；不可构造的两类只要求存在明确类别与文案
**And** 全过程无用户交互、无授权弹窗、不请求任何用户资料；函数被调用时尚无会话，因此关闭平台前置 JWT 校验并在函数内自行校验输入

**And** 只有「待取餐」的本人订单可以被确认；其他状态返回明确的拒绝结果
**And** 重复确认是幂等的：第二次确认不报错、不改变状态、不修改完成时间
**And** 与推进并发时结果确定：要么基于更新后的状态成功完成，要么返回明确的「状态已变化」结果，不产生中间态
**And** 该操作是用户主动行为，不需要额外凭证（不做取餐码核销）

### Story 4.5: 状态机与并发行为的测试

As a 后端作者，
I want 状态机与并发的关键边界被测试钉住，
So that 重复发号、状态倒退这类事故不会悄悄出现。

**Requirements:** FR-P2-19; AR-8

**Acceptance Criteria:**

**Given** 重建后的空库
**When** 运行数据库测试
**Then** 断言非法迁移被拒绝且订单当前状态不变
**And** 断言推进重复执行幂等（不产生第二个取杯号、不跳状态）
**And** 断言同一自然日内并发推进不产生重复取杯号（跨日允许重复）
**And** 断言重复催单后的推进时刻不早于也不晚于「原定时刻与催单时刻 + 提前量中的较早者」
**And** 断言兜底扫描重跑不破坏已有数据
**And** 测试仍以一条命令运行，失败时能定位到具体函数

## Epic 5: 我的订单：归属隔离与测试证明

用户只能读到自己的订单列表与详情（读取时顺带推进到点订单）；换一个身份读不到他人订单、未认证读不到任何订单、拿到发布密钥也写不进一张金额自定的订单——全部由可重复运行的测试给出证据。

### Story 5.1: 我的订单列表

As a 已登录用户，
I want 分页看到自己的订单（按时间倒序），
So that 我能回到最近点过的那一单。

**Requirements:** FR-P2-14; AR-13, AR-16, AR-17, NFR1

**Acceptance Criteria:**

**Given** 已登录会话
**When** 读取订单列表
**Then** 结果只包含本人订单；他人订单在同一次调用中不可能出现
**And** 排序为创建时间倒序且稳定；分页默认每页 20 条、参数有上限，翻页过程中不重复、不遗漏已存在订单
**And** 返回结构包含订单号、状态、就餐方式、商品摘要、金额与包装费、备注、取杯号、创建时间，字段名与空值规则由同一映射产出
**And** 函数内先推进调用者自己到点的订单，再返回结果——不会观察到「已到点却仍在制作中」
**And** 未进入「待取餐」的订单取杯号返回空值而非空串；时间按门店本地时区输出为 `YYYY-MM-DD HH:mm:ss`
**Given** 未登录请求
**When** 读取订单列表
**Then** 请求被拒绝，而不是返回空列表

### Story 5.2: 订单详情

As a 已登录用户，
I want 看到某一单的完整信息，
So that 我能核对商品、金额与门店信息。

**Requirements:** FR-P2-15; AR-15, AR-17

**Acceptance Criteria:**

**Given** 本人订单
**When** 读取订单详情
**Then** 返回商品明细（含快照与数量）、门店信息（名称、地址、电话）、订单号、下单时间、就餐方式、备注与金额
**And** 详情与列表读取自同一数据源、同一映射实现，不存在两套口径；时间与金额格式与列表完全一致
**Given** 他人的订单标识
**When** 读取订单详情
**Then** 请求被拒绝，且拒绝方式不泄露该订单是否存在（与「不存在」返回同一结果）

### Story 5.3: 归属隔离与策略边界的测试证明

As a 作品集作者，
I want 数据归属与安全边界有可重复运行的测试证据，
So that 「换个人就读不到」是被证明的事实，而不是「应该没问题」。

**Requirements:** FR-P2-18, FR-P2-19; AR-5, AR-12, AR-18, AR-20

**Acceptance Criteria:**

**Given** 两个不同身份与一个未认证身份
**When** 运行数据库测试
**Then** 断言三类边界：他人数据不可见、他人数据不可写、未认证不可读
**And** 断言归属的两处表达（行级策略与函数内部谓词）等价：同一身份经函数与经裸表读取，可见行集合相同
**And** 断言拿到发布密钥直接访问数据库时读不到他人订单，且无法自行写入一张金额自定的订单
**And** 断言内部表（身份映射、取杯号计数器）对客户端完全不可达：不携带任何面向客户端的策略，且默认授权已撤销
**And** 断言所有对外暴露的表都启用了行级访问控制（逐张确认，无遗漏）
**And** 测试以一条命令运行，在重建后的空库上直接通过
**Given** 客户端侧的交付物（小程序包、客户端源码、客户端可读配置）
**When** 检查密钥边界
**Then** 其中不存在服务端密钥——以仓库级搜索或人工核对作为证据，不要求数据库测试覆盖

### Story 5.4: 干净环境端到端重建验收

**Requirements:** FR-P2-16; AR-3, AR-6

**When** 从仓库重建环境
**Then** 结构、目录数据与图片全部就位，全程不需要点控制台、不需要执行未入仓的 SQL、不需要手工上传文件
**And** 本地与云端的结构一致，以两边迁移列表一致为证据
**And** 重建后立即可以完成登录、下单与订单查询，不需要额外修补
**And** 重建后的库上运行数据库测试直接通过

### Story 5.5: 两身份隔离的真机验证

As a 作品集作者，
I want 用两个真实身份走一遍「下单 → 换身份 → 查不到」，
So that 数据隔离被亲眼证明，而不是只存在于测试断言里。

**Requirements:** FR-P2-14, FR-P2-15, FR-P2-18, FR-P2-9; AR-9; UJ-P2-1

**Acceptance Criteria:**

**Given** 真机 A 与真机 B（或同一设备上的两个微信号）均为该小程序的开发/体验成员，且后端实例可达
**When** 身份 A 携带会话提交一笔订单，随后身份 B 携带会话查询订单列表
**Then** 身份 B 的结果里没有 A 的那张单；改用身份 A 的会话查询时它就在那里
**And** 在数据库里该订单明确挂在 A 的 OpenID 所映射的用户下
**And** 两台设备重启小程序后仍是各自的身份，不需要重新登录
**Given** 登录凭证已失效（微信侧返回凭证过期/已用）
**When** 用户重试
**Then** 看到明确提示且可重试，重试不产生第二个身份
**And** 本故事的证据形式为「实现方式说明 + 人工验证记录」，不要求自动化覆盖
**And** 若第二台设备或第二个微信号不可得，按 PRD R-9 降级为沙箱内两套身份验证，并在文档中如实记录降级
