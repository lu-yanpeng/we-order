# We-Order Phase 2 — 附录（机制与选型）

本文件收集对话中出现、但不该写进 PRD 正文的内容：机制/传输选型、被否决方案的取舍理由、技术调研结论、以及下游架构文档需要接手的细节。PRD 正文里凡是标注"见 addendum 第 X 节"的地方，都能在这里找到理由。

## A. 身份与登录机制（路线已定）

- 微信小程序端通过 `wx.login` 取 code，服务端调用凭证校验接口换取 `openid`（`AppSecret` 只能留在服务端，放边缘函数 secrets）。
- **已定路线**：边缘函数用固定凭证找到或创建身份映射 → 创建/复用用户 → 生成一次性登录令牌并在**函数内立即兑换为平台标准会话**（访问凭证 + 刷新凭证）→ 把会话返回客户端。令牌不落到客户端：登录接口一次调用完成，单次消费与时效由平台保证。
- **已否决路线：自签 JWT**。理由：平台正在把 JWT 签名密钥迁移为非对称密钥，任何自行用项目密钥签名/校验的实现都会在密钥轮换后失效。自签方案在社区教程里仍常见，但属于技术债。
- `openid` 与用户一一对应，存于身份映射；同一 openid 跨设备重登即同一用户。
- 按 email 找回既有平台用户经只读 RPC `find_user_by_email`（security definer 查 `auth.users`，只有服务端密钥可执行；不暴露 auth schema、不直连数据库）。不用 `admin.generateLink` 当反查——已实测它对不存在的 email 会顺手创建一个未确认用户。
- 平台原生匿名登录（`signInAnonymously`）**不采用**：它拿不到 openid（openid 只能服务端换取），且匿名用户有 IP 限流、无自动清理，与本项目的身份模型不匹配。
- 已知并发行为：同一 email 新生成的一次性令牌会让之前未消费的令牌作废，因此同一身份的两个并发登录可能有一个拿到可重试的 `session_failed`。不做服务端重试（上一个版本的多次重试被判定为过度设计），客户端重试即可。
- 风险：本项目不接真实微信支付，因此不涉及商户资质；但凭证校验需要可用的小程序主体（正式 AppID 或测试号），且真机验证需要第二个已授权微信号——两条都已列入 PRD §7 的前置资产。

## B. 价格可信性机制

- 前端提交订单只传：商品 id + 规格选择 + 数量（+ 备注、就餐方式）。
- 服务端依据数据库中的价格规则重新计算每一项单价与总额，**忽略前端传入的任何金额**。
- 订单明细落库时写入商品名、规格选择（结构化）、规格摘要文本（服务端按选项文案生成）、单价与数量快照，使商品改价/改名不影响历史订单，且「再来一单」能按原规格还原。
- **写路径封闭**：订单与订单明细不对客户端开放直接写入授权（无 INSERT 权限），下单只能经由服务端函数——否则"服务端重算"可以被一条直接写表的请求绕过。归属用户取自会话身份，不接受客户端传入。

## C. 订单状态流转机制

- 状态机：`cooking`（制作中）→ `pickup`（待取餐）→ `completed`（已完成）。不引入 `cancelled`。
- **推进方式：读取时判定 + 周期兜底**。订单上记录"推进时刻"（`ready_at`），任何一次读取都由服务端判定是否到点并推进；另有周期性兜底扫描，保证无人读取时也会推进。
  - 为什么不纯用定时任务：平台**不支持"事件发生后延时 N 秒执行一次"**（这类需求没有官方机制），周期任务的最小间隔虽可做到秒级，但它是"周期"而非"事件相对"，用它做单笔订单的精确时刻会产生抖动与无意义的唤醒。
  - 为什么不纯用客户端回调：状态推进必须由服务端负责，客户端不在线时订单不能卡住。
  - 代价：状态在无人读取时"尚未物化"（数据库里仍是 `cooking`，但逻辑上已到点）。兜底扫描周期决定这个窗口的上限。
- **已定参数**：默认推进时长为下单后 **15 秒**；催单把推进时刻提前到「催单时刻 + **3 秒**」。两者都是**可配置的演示参数**，不是业务规则——真实门店场景为分钟级，配置化是为了在被追问"为什么 15 秒就出餐"时能给出解释。
- 催单的推进时刻取「原定时刻」与「催单时刻 + 3 秒」中**较早者**（`min`），因此重复催单幂等：既不会更早，也不会忽然后延。
- **并发控制**：状态变更一律用"带条件的一次性更新"（仅当仍处于预期状态时才写入），而不是先读后判再写；催单与推进的竞争、两次扫描的重叠、确认取杯与推进的交错都由这一点收敛。
- 取杯号：外形为字母前缀 + 四位数字（`A-0008`），同一前缀用尽后进入下一个字母（`A-9999 → B-0001`），A-Z 合计每日 259,974 个号；在**门店本地时区的同一自然日**内唯一；并发分配靠原子计数（当日计数 + 唯一约束）保证，不靠"查最大值再加一"。（2026-09-21 修订：原为沿用 Phase 1 的 `A-08` 两位数字，ly 裁定改为四位并加前缀轮转。2026-09-22 修订：发号时机由「推进到待取餐时分配」前移到**下单时分配**——制作中的订单即可报号向店员询问进度；发号日期取下单时刻的门店本地自然日、一经分配不可变；「能否取餐」只由状态表达。已交付 Story 4.1 的发号时机随之修订，见 epics.md 的 Story 4.4。）
- 用户确认取杯：`pickup` → `completed`。
- **用户不确认时的兜底：超时自动完成**（2026-09-22 修订新增）。订单进入「待取餐」时按门店配置的等待时长（演示默认 30 秒，真实场景为分钟级）算出**自动完成时刻**写入订单，超时后由服务端自动置为「已完成」——用户取完餐忘了点确认，订单也不会永远挂在「待取餐」。触发方式与推进同一套：**读取时判定 + 周期兜底扫描**（复用同一个周期任务），并与用户确认取杯共用同一条 `pickup→completed` 迁移实现，只是触发源不同。备选（已否决）：依赖平台"事件发生后延时 N 秒执行一次"——平台没有这类调度；且时刻在进入待取餐时已经确定，周期扫描足够。
- 备选（已否决）：纯用户触发（催单后几秒直接变「待取餐」）——语义不成立，且展示不出服务端在跑；只做机制不做触发——演示价值不足。

## D. 数据访问与迁移策略

- 商品/分类/规格由 migration + seed 定义，Phase 2 仅提供只读接口；写入路径留给 Phase 4 商家后台。
- 迁移与种子数据入仓，目标是任何人 clone 后可用一条命令重建数据库（可复现性为面试亮点之一）。
- **对象存储进入迁移范围**：桶与读取策略由迁移创建，图片对象由入仓脚本灌入。否则"零手工步骤重建"不成立——只重建关系库会留下指向不存在对象的图片引用。
- 购物车不上云，沿用 Phase 1 本地存储，下单时一次性提交。
- 目录读取公开（无需登录）：浏览菜单与 Phase 1 行为一致。

## E. 实时推送（Realtime）调研结论

- 结论：Phase 2 不做 Realtime 决策与配置，推迟到 Phase 3 联调时评估。
- 依据（Ly 调研）：微信小程序环境没有原生浏览器 WebSocket；社区里针对 supabase 的小程序适配器多已数年未维护。
- Plan B：前端轮询订单状态。
- 下游影响：Phase 3 需要在「订阅」与「轮询」之间做一次正式选型；若未来要启用订阅，Phase 2 侧只需补 publication 配置与 RLS 兼容性验证。

## F. 门店建模

- 建立门店表（即使只有一家店），订单通过 `store_id` 关联，同时保存门店名称/地址/电话快照。
- 理由：门店信息硬编码在小程序端意味着每次变更都要重新提审发版；入库后改一条记录即生效，且 Phase 4 商家后台按门店过滤天然可用。
- 电话入快照：Phase 1 的订单详情页本就展示门店电话，不入快照会在 Phase 3 立刻缺字段。
- 明确不做：多门店切换、门店定位、门店运营时间管理。

## G. 客户端接入方式（已定）

- 小程序端**不引入 supabase-js，也不引入社区适配库**：用手写 HTTP 调用（`wx.request`）+ 会话携带的方式访问 REST/RPC。
- 理由：官方 SDK 依赖浏览器的 `fetch`/`WebSocket`/`FormData` 等能力，小程序环境需要补丁或不维护的第三方适配器；手写调用无依赖、可控，且配合生成的类型仍有形状约束。
- 代价：会话自动续期需要自己实现（判断过期 → 用刷新凭证换新 → 重试原请求）。
- 下游影响（Phase 3）：类型安全在客户端一侧取决于调用方式；PRD 的 FR-P2-17 因此只承诺"类型可生成并入仓"，不承诺客户端的编译期保护。

## H. 平台能力与坑（调研结论摘要）

- **域名**：小程序可请求域名必须 ICP 备案，Supabase 域名无法加入白名单。开发期绕过靠开发者工具"不校验合法域名"、真机/体验版"打开调试"、同一局域网 IP 直连（不要求 https）；正式发布需备案域名反代或经平台云托管中转。
- **凭证校验接口**：不需要 IP 白名单（白名单只约束获取平台访问凭证类接口）；有频率限制。
- **错误码（用于 PRD 的错误类别映射）**：`40013` AppID 无效 · `40125` AppSecret 无效 · `40029` 凭证无效 · `40163` 凭证已被使用 · `42003` 凭证已过期 · `40226` 高风险用户被拦截 · `45011` 频率超限 · `45009` 日调用量超限 · `-1` 系统繁忙。其中前五类可由受控输入构造并断言，后四类只能做映射不做自动化复现。
- **边缘函数**：内存与运行时长受限，无持久化磁盘，冷启动数百毫秒；密钥通过平台 secret 配置注入，密钥名不能以 `SUPABASE_` 开头。
- **调度**：周期任务最小间隔可做到秒级（需较新的 Postgres 版本），但**不支持事件相对的一次性延时调度**；并发与单次时长有限制。
- **密钥**：服务端密钥绕过一切数据访问策略，绝不可出现在客户端；发布密钥可公开，权限完全由策略决定。
- **测试**：数据库层策略测试可用 pgTAP，通过 `supabase test db` 在本地容器内运行。
- **类型**：`supabase gen types typescript` 生成类型；嵌套查询的返回形状与表类型不同，JSON 快照字段需要手工类型覆盖。
