# PRD: We-Order 点餐小程序 — Phase 2 Supabase 后端

> **三分钟速读**（完全版约 500 行，读懂这段就不会迷路；细节按需往下翻）
>
> - **这一阶段干什么**：把 Phase 1 的本地 Mock 换成真实后端，让订单真正归属于某个用户。**小程序界面不会有任何变化**——换数据源是 Phase 3 的工作。
> - **最大的一块**：微信静默登录。小程序取一次性凭证 → 服务端换取 OpenID → 签发可续期的会话。这是 Phase 2 最容易踩坑、也最能体现代码能力的地方。
> - **服务端说了算**：订单金额由服务端按库内价格规则重算（前端传的金额一律不信）、订单号由服务端生成、取杯号在下单时即分配、订单状态由服务端在 15 秒后推进到「待取餐」；点催单把这一刻提前到 3 秒后。订单只能经由服务端函数创建，客户端没有直接写表的权限。
> - **四个亮点**（同时是成功指标）：数据访问策略（RLS）、边缘函数承载服务端逻辑、数据库生成的类型入仓、任何人都能一条命令重建数据库并跑测试。
> - **最大的外部约束**：微信不允许未备案域名，Supabase 的域名加不进白名单。开发与演示靠三条路绕过——开发者工具勾选不校验、真机打开调试模式、同一局域网内 IP 直连；正式发布需要另行解决，但不阻塞本阶段。
> - **两个前提资产**：一个可用的小程序主体（AppID/AppSecret）和一个已授权的第二微信号——没有它们，真机登录验证与"换身份证明隔离"都无法完成。
> - **明确不做**：真实支付、购物车上云、多门店、商家后台、订单取消、优惠券、实时推送、云端实例与图片对象入仓（见修订记录）、端到端测试与部署流水线。
> - **怎么算成功**：干净机器能一条命令重建数据库；换一个身份就读不到别人的订单（且有测试证明）；对接 Phase 3 不推倒重建；真机登录链路可用。

## 1. 愿景

Phase 1 交出了一套完整的小程序页面，但它的数据是假的：订单存在手机本地、商品写死在包里、任何人打开看到的都是同一份内容。Phase 2 把数据搬到一个所有设备都能访问的地方，并且**每个用户只能看见自己的东西**。

这件事的价值不体现在界面上——Phase 2 完成后小程序看起来不会有任何变化（界面仍是 Phase 1 那一套，数据源仍是 Mock，因为对接是 Phase 3 的工作）。改变的是三件事：项目第一次有了"多用户"这个概念，订单归属到具体身份，换台设备、换个人，看到的东西就不同；第一次有了真正的服务端逻辑，金额由服务端算、状态由服务端推、错误由服务端定义；Phase 3 的对接成本被前置消化，最容易返工的三样东西——数据形状、金额口径、数据归属——在这里定下来。

面试官最容易问倒前端候选人的那个问题是：*"你说的这个订单，是存在哪儿的？别人能看到吗？"* 答案由 Phase 2 给出。因此这一阶段有意把力气花在作品集项目里常被跳过的四件事上：数据访问策略、可复现的数据库重建、服务端金额重算，以及证明前三件事确实成立的测试。

## 2. 目标用户

### 2.1 要完成的工作（Jobs To Be Done）

- **作为作品集作者（Ly）**：我需要一个真实的后端，让我除了"页面做得好看"之外，还能证明自己理解服务端、数据归属与安全边界——这是我投递高级前端岗位时最容易被质疑的一块。
- **作为 Phase 3 的对接者（Ly）**：我需要一套"接上去就能用"的接口与类型。对接期我只想替换数据源，不想推倒重建——补字段、加个可选参数这类小改我能接受，重做数据模型或重写接口契约才是真麻烦。
- **作为 Phase 4 的开发者（Ly）**：我需要商品、门店、订单这三类主数据已经在库里，且结构经得起商家后台的读写；Phase 4 应该只需要加界面和写路径，不需要重新建表。
- **作为面试官（隐含受众）**：我需要看到候选人能说清"数据属于谁"，能在被追问"前端改价怎么办""我怎么保证读不到别人的订单"时给出确定答案，而不是"应该没问题吧"。

### 2.2 非用户（v1）

- **真实顾客**：Phase 2 不新增任何面向顾客的功能，也不接真实支付，不具备承载真实交易的能力与意图。
- **商家与店员**：Phase 4 才提供操作界面；Phase 2 只提供机制，没有给商家用的入口。
- **外部开发者**：不对外提供 API、不做对外开放，所有接口只服务本项目的小程序与后台。

### 2.3 关键旅程

Phase 2 **不改变任何终端用户体验**，因此不新增面向顾客的旅程：Phase 1 的 `UJ-1`（面试现场演示完整点餐流程）依然是唯一的产品旅程基准。Phase 2 需要被验证的是下面这条开发侧旅程——它只依赖 Phase 2 真正会改动的东西。

> **UJ-P2-1. Ly 用两个身份验证"数据是我的"。**
> Ly 是作品集作者，刚把 Phase 2 开发完，需要确认后端真的按人隔离数据，而不是"碰巧看起来对"。
> **入口状态**：Phase 2 已完成；真机 A 与真机 B（或同一台设备上的两个微信号）均为该小程序的开发/体验成员，后端实例可达。
> **路径**：真机 A 打开小程序 → 静默完成登录，取得身份 A 的会话 → 用接口工具（携带身份 A 的会话）提交一笔订单 → 真机 B 打开小程序、完成登录取得身份 B 的会话 → 用接口工具（携带身份 B 的会话）查询订单列表。
> **高潮**：身份 B 的查询结果里没有身份 A 的那张单；而在数据库里，这张单明确挂在 A 的 OpenID 所映射的用户下。再用携带身份 A 会话的请求查询，它就在那里。
> **结束状态**：数据隔离被亲眼证明；两台设备重启小程序后仍是各自的身份，不需要重新登录。
> **边界情况**：若登录凭证已失效（微信侧返回凭证过期/已用），用户看到明确提示并可重试，且重试不产生第二个身份。
> **为什么下单和查询用接口工具而不是小程序界面**：Phase 2 对小程序侧的改动只有登录链路与最小验证入口（§6 范围护栏），下单与查询的界面属于 Phase 3。用接口工具携带真实会话去验证，证明的正是后端本身；换成界面按钮只会在 Phase 3 变成重复验证。

## 3. 术语表

- **OpenID**——微信为"某个用户 + 某个小程序"组合分配的唯一标识。Phase 2 里它是用户身份的唯一来源。本项目只存 OpenID，不存昵称、头像、手机号等任何个人信息。
- **身份映射（Identity Mapping）**——OpenID 与系统用户之间的对应关系。一个 OpenID 对应且仅对应一个用户；映射一旦建立不可被其他 OpenID 复用。
- **会话（Session）**——登录成功后签发给客户端的一套凭证，由**访问凭证（Access Token）**与**刷新凭证（Refresh Token）**组成。访问凭证短期有效；过期后由刷新凭证换新，对调用方透明。
- **静默登录**——不需要用户点击授权、不索要任何资料的登录方式。Phase 2 的登录全部是静默登录。
- **服务端密钥（Secret Key）**——拥有绕过数据访问策略权限的高权限凭证。只允许存在于服务端；**任何情况下不得出现在客户端**。
- **发布密钥（Publishable Key）**——可随客户端分发的低权限凭证。它的权限完全由数据访问策略决定，因此可以公开。
- **数据访问策略（RLS，Row Level Security）**——数据库层的行级访问控制：即使有人拿到发布密钥直接访问数据库，也只能看到策略允许他看到的行。
- **订单快照（Order Snapshot）**——下单时刻写入订单明细的副本：商品名、规格选择（结构化）、规格摘要文本、单价、数量。商品之后改名或改价，不影响历史订单；「再来一单」依赖其中的规格选择副本。
- **服务端金额重算（Server-side Recalculation）**——订单金额完全由服务端依据库内价格规则计算，客户端提交的任何金额都不被信任。
- **幂等（Idempotent）**——同一操作重复执行与执行一次的结果相同。Phase 2 用幂等保证"网络重试不会产生两张订单""重复确认取杯不会报错"。幂等标识与用户绑定，不可跨用户复用。
- **取杯号（Pickup Code）**——订单**创建时**分配的短编号，形如 `A-0008`（字母前缀 + 四位数字），在门店本地时区的同一自然日内唯一、跨日可重复；制作中即可凭它向店员询问进度，「能否取餐」只由订单状态表达，号本身不是可取的信号。
- **推进时刻（Ready At）**——服务端记录的时刻，到期后订单应从「制作中」变为「待取餐」。催单的作用就是把它提前。
- **迁移（Migration）**——以文件形式记录、可重复执行的数据库结构变更。Phase 2 的全部结构变更都必须以迁移形式入仓；对象存储的桶与读取策略、定时任务同样必须以**声明式**方式入仓（迁移 SQL 或 config.toml + seed 任一），不得依赖控制台手工操作。
- **种子数据（Seed）**——在空库上灌入的初始数据（分类、商品、规格、门店）。种子数据只覆盖目录类数据，不包含订单。
- **边缘函数（Edge Function）**——部署在平台边缘的服务端函数，Phase 2 用于与微信服务器交互（换取 OpenID）等必须放在服务端的逻辑。
- **服务端函数（RPC）**——数据库内可直接调用的函数，作为一次事务性的服务端操作被调用。Phase 2 的下单与状态流转走服务端函数，以保证原子性；客户端不直接写入这两张表。
- **类型契约（Type Contract）**——由数据库结构生成的 TypeScript 类型定义，入仓版本管理。它是服务端返回与客户端消费的形状来源。
- **可售状态（Availability）**——商品的三态：在售/售罄/下架。**下架**的商品不进入目录读取结果；**售罄**的商品保留在结果中并随结果返回状态，由客户端置灰呈现。
- **目录数据（Catalog）**——分类、商品、规格组、规格选项、门店、商品图片的总称。全部可公开读取，写入路径留待 Phase 4。

## 4. 功能需求

### 4.1 身份与登录

**描述：** 小程序启动后静默完成登录，把用户与一个 OpenID 绑定起来，并取得一套可续期的会话。登录不是一次性的动作，而是"每次启动都确保有有效身份"的持续状态。Phase 2 只做静默登录，不索取任何用户资料。本组实现 UJ-P2-1。

#### FR-P2-1: 微信登录换取身份

用户可以在小程序内发起登录，由系统用微信下发的一次性凭证换取该用户的 OpenID。

**验收条件（可测）：**
- 客户端取得的一次性凭证只能被消费一次；同一凭证重复提交时返回明确的「凭证已使用」/「凭证已过期」语义，且不建立新身份。
- 换取 OpenID 的调用**只在服务端发生**；AppSecret 不出现在小程序包、客户端源码或任何客户端可读取的配置中。
- 换取失败时按原因区分，不做成统一的"登录失败"。分类必须覆盖：AppID 无效、密钥无效、凭证无效、凭证过期或已用、高风险用户被拦截、频率超限。
- 其中**可构造的原因**（AppID 无效、密钥无效、凭证无效、凭证过期或已用）可以用受控输入注入并断言分类正确；**不可构造的原因**（高风险用户被拦截、频率超限）只要求存在明确的错误类别与对应文案，不要求自动化复现。
- 全过程无用户交互、无授权弹窗、不请求任何用户资料。

#### FR-P2-2: 身份映射与用户建立

系统将 OpenID 稳定映射到一个用户；同一 OpenID 重复登录得到同一个用户，不同 OpenID 得到不同用户。

**验收条件（可测）：**
- 首次登录创建用户与映射；再次登录复用既有映射，不产生重复用户。
- 同一 OpenID 的并发首次登录（短时间内两次请求）只会产生一个用户。
- 已建立的映射不可被另一个 OpenID 复用。

#### FR-P2-3: 会话签发

登录成功后，系统向客户端签发一套可续期的会话凭证（访问凭证 + 刷新凭证）。

**验收条件（可测）：**
- 客户端凭该会话即可访问受数据访问策略保护的数据，无需额外凭证。
- 会话所标识的主体与 OpenID 映射到的用户一致。
- 会话使用平台标准签发机制，**不使用自签 JWT 方案**（已定路线与否决理由见 docs/phase-2/addendum.md §A）。

#### FR-P2-4: 会话持久化与自动续期

用户重新打开小程序后无需再次登录即可继续使用。

**验收条件（可测）：**
- 会话凭证持久化在客户端本地存储中，应用重启后可恢复，不需要用户再次操作。
- 访问凭证过期后，再次发起任一受保护请求仍然返回成功——续期对调用方透明，不出现要求用户重新登录的中断，也不出现同一个操作先失败再重试的成功。
- 续期不可用时（刷新凭证失效），回退为重新静默登录，且不会产生第二个身份。

#### FR-P2-5: 登录失败的可见反馈

登录无法完成时，用户能看到明确且不暴露内部细节的提示。

**验收条件（可测）：**
- "网络不可达""微信侧限流""凭证失效"三类情况对应三个不同的错误类别与不同文案。
- 提示与日志中都不包含 AppSecret、服务端密钥、内部堆栈或数据库细节（密钥边界见 FR-P2-18）。
- 失败后用户可重试；重试不会留下半登录状态（既不产生孤儿用户，也不残留不可用的会话）。

### 4.2 商品目录（只读）

**描述：** 后端提供菜单、规格、门店与商品图片的读取能力，作为 Phase 3 替换 Phase 1 Mock 数据的来源。目录数据可在未登录状态下读取——浏览菜单不需要身份，和 Phase 1 的行为保持一致。本组为 UJ-P2-1 提供下单所需的真实数据。

#### FR-P2-6: 分类与商品读取

用户可以读取分类、商品、规格组与规格选项，未登录状态下同样可访问。

**验收条件（可测）：**
- 返回的数据以后端字段名为准（snake_case、与库中列名一致）；字段集合与 Phase 1 的 `Category` / `Product` / `SpecGroup` / `SpecOption` 语义一一对应，Phase 3 由前端类型向生成类型对齐（见 §5 兼容性）。
- 商品具备**可售状态**（在售/售罄/下架）：**下架**的商品不出现在结果中；**售罄**的商品保留在结果中并返回 `availability` 状态，供客户端置灰；分类下没有任何「非下架」商品时该分类不返回。
- `sales`（月销量）是种子数据里维护的静态展示值，**不随订单聚合计算**（本阶段不做统计）。
- 规格组的"多选"语义（Phase 1 中的 `addons`）在数据中保留。
- 规格选项的加价金额可被服务端用于订单金额重算——**同一份价格数据既是展示来源，也是计价来源**，不存在两套价格。
- 未登录请求不被拒绝。

#### FR-P2-7: 商品图片读取

用户可以读取商品图片。

**验收条件（可测）：**
- 图片由对象存储提供，未登录状态可读取。
- 存储桶与读取策略、图片对象以**声明式**方式入仓（迁移 SQL 或 config.toml + seed 任一，与 FR-P2-16 同一要求），不依赖任何控制台手工操作。
- 商品记录中的图片引用与存储中的对象一致：重建之后不存在"引用存在但对象缺失"的商品。
- 图片缺失或加载失败不阻塞商品列表渲染。
- Phase 2 只提供图片的读取与存放能力，**图片上传路径不在本阶段**（见 §9）。

#### FR-P2-8: 门店读取

系统提供当前门店信息，供下单与订单展示使用。

**验收条件（可测）：**
- 门店名称、地址、电话由一个查询得到；系统中不存在第二处门店数据来源（例如客户端内置常量）。
- 提交订单时记录门店引用**与门店快照**（名称、地址、电话），使门店信息后续变更不影响历史订单。
- Phase 2 只有一家门店，不提供门店列表、切换或定位能力。

### 4.3 下单

**描述：** 已登录用户提交订单，服务端校验输入、重算金额、生成订单号，并在同一事务内写入订单与明细。这是 Phase 2 唯一的写路径入口，也是"前端说什么都不算数"这条原则最集中的体现。本组实现 UJ-P2-1。

#### FR-P2-9: 提交订单与金额重算

已登录用户可以提交订单；系统校验输入、按库内价格规则重算金额，并把订单与其明细一并落库。

**验收条件（可测）：**
- **写入路径唯一**：订单与订单明细不向客户端开放直接写入权限，下单只能经由服务端函数完成——不存在"客户端直接向订单表插入一行"的可用路径。
- **归属不可伪造**：订单所属用户取自会话身份；客户端传入的任何用户标识都被忽略。
- 客户端提交的内容只包含：商品引用、规格选择、数量、就餐方式、备注；**不包含金额**。
- 逐行单价与订单总额由服务端依据库内价格规则计算，落库金额等于重算结果；客户端提交的金额若存在则被忽略。
- 金额规则沿用 Phase 1：基础价 + 规格加价；外带计入包装费 2.00 元、堂食 0 元。金额以元为单位、保留两位小数。`[ASSUMPTION: 包装费与堂食的金额规则沿袭 Phase 1]`
- 输入非法时整单被拒绝且不留下任何数据：商品不存在或不可售、规格选项不属于该商品、数量非正数、就餐方式取值非法。
- 订单与订单明细在同一事务内写入——不存在"有单无明细"的中间态。
- **订单快照完整**：订单明细保存商品名、规格选择（规格组 → 选项的结构化副本，供 Phase 3 的「再来一单」还原）、规格摘要文本（由服务端依据选项文案生成，不接受客户端提供的摘要文本）、单价与数量。商品之后改名或改价不影响该订单。
- 订单号由服务端生成，外形为 18 位纯数字（门店本地时间 `YYYYMMDDHHmmss` + 4 位随机尾号）且全局唯一；客户端不再自行生成订单号。`[ASSUMPTION: 18 位结构号；Phase 1 原型的 SG + 8 位随机号不再沿用]`
- 备注未传或为空时，服务端落库为「无备注要求」（沿用 Phase 1 行为）。
- 新订单初始状态为「制作中」，并于**下单时分配取杯号**（见 FR-P2-11），写入推进时刻；创建时间由服务端记录，客户端时间不参与。
- 时间在库中以带时区的时间戳存储，接口返回时按 Phase 1 的外形 `YYYY-MM-DD HH:mm:ss`（门店本地时区）输出，使 Phase 3 无需改动展示。`[ASSUMPTION: 时间格式沿袭 Phase 1]`

#### FR-P2-10: 重复提交防护

用户因网络重试或连续点击而重复提交同一笔订单时，不会产生多张订单。

**验收条件（可测）：**
- 客户端提交时携带幂等标识；携带同一标识的重复提交返回同一张订单，且不重复写入任何数据。
- **幂等标识与用户绑定**：同一标识只对同一用户有效；其他用户携带该标识提交时，只会得到属于自己的新订单或明确拒绝，绝不会取回他人的订单。
- 使用不同标识的两次提交会产生两张订单（用户确实想买两份时，行为符合直觉）。
- 幂等保护在并发情况下同样成立（同一标识的两个请求同时到达，只落一张订单）。

### 4.4 订单状态流转

**描述：** 订单状态遵循固定生命周期：`制作中 → 待取餐 → 已完成`。推进由服务端判定与执行——不依赖用户操作触发，也不要求客户端在线。Phase 4 的商家后台未来会成为另一个触发源，但本阶段不提供商家操作界面。本组的验证方式见 FR-P2-11 与 FR-P2-19（不在 UJ-P2-1 的路径上）。

#### FR-P2-11: 状态推进与取杯号生成

订单在**创建时**即分配取杯号；创建后经过一段固定时长（默认下单后 **15 秒**）进入「待取餐」。推进的判定与执行都在服务端：任何一次对订单的读取都会由服务端判定是否到点并完成推进；另有一个周期性的兜底扫描，保证即使无人读取，订单也不会永久停留在「制作中」。`[ASSUMPTION: 15 秒是演示参数而非业务规则——推进时长应可配置，真实门店场景为分钟级]`

**验收条件（可测）：**
- 推进的判定与执行都在服务端完成：客户端只发起读取，不参与判定，也不能通过传参改变推进时刻或状态。
- 有人读取时到点即推进，观察到的结果与设定时长一致；无人读取时，订单也会在一个兜底扫描周期内被推进。
- 推进时长可配置，不写死在判断逻辑里。
- **下单时分配取杯号**：在门店本地时区的同一自然日内唯一（跨日允许重复），外形为字母前缀 + 四位数字（如 `A-0008`），同一字母用尽后进入下一个字母（`A-9999 → B-0001`）；发号日期取下单时刻的门店本地自然日，不随后续状态变化重算。
- **取杯号一经分配不可变**：推进与催单都不写取杯号；「能否取餐」只由状态表达，号不是可取的信号（制作中即可报号向店员询问进度）。
- **并发安全**：并发下单不产生重复取杯号（原子计数 + 唯一约束保证）；推进与用户操作（催单、确认取杯）同时发生时，最终状态唯一。
- 推进过程幂等：重复执行不会跳状态，也不会改写取杯号。
- 只接受合法迁移（制作中→待取餐→已完成）；任何非法迁移被拒绝，且不改变订单当前状态。
- 推进任务失败后可安全重跑，重跑不会破坏已有数据。

#### FR-P2-12: 催单加速

已登录用户可以对本人处于「制作中」的订单发起催单，系统把该订单的推进时刻提前到「当前时刻 + 3 秒」。`[ASSUMPTION: 3 秒为演示参数，同样可配置]`

**验收条件（可测）：**
- 催单的作用是**把推进时刻提前**，而不是由催单请求直接把订单置为「待取餐」——状态变更仍由推进机制完成。
- 推进时刻取「原定时刻」与「催单时刻 + 3 秒」中**较早者**；该更新是原子的，与推进并发发生时不会导致推进被延后或丢失。
- 重复催单既不会让出餐更早，也不会让它变晚（不存在"催得越多出餐越快"的叠加效应）。
- 对**非本人**订单发起催单时被拒绝，且拒绝方式不泄露该订单是否存在。
- 对**本人**但状态已不是「制作中」的订单发起催单时，返回明确的「当前状态不可催单」结果——对本人的订单，语义准确优先于防泄露。

#### FR-P2-13: 确认取杯

已登录用户可以把本人处于「待取餐」的订单置为「已完成」；用户不确认时，订单在进入「待取餐」一段时间后由服务端自动完成，作为兜底。

**验收条件（可测）：**
- 只有「待取餐」状态的本人订单可以被确认取杯；其他状态返回明确的拒绝结果。
- 重复确认是幂等的：第二次确认不报错、不改变状态、不修改完成时间；确认一张已被超时自动完成的订单同样返回成功且不改写完成时间。
- 与推进并发时（用户点击的瞬间订单刚好被推进或尚未推进），结果确定：要么基于更新后的状态成功完成，要么返回明确的「状态已变化」结果，不产生中间态。
- 该操作是用户主动行为，不需要额外凭证（不做取餐码核销）。
- **超时自动完成**：订单进入「待取餐」时按门店配置算出自动完成时刻写入订单，超时后由服务端自动置为「已完成」——不依赖用户操作、不要求客户端在线；读取订单时即时完成（读时兜底），周期扫描对全部超时订单兜底，两者共用同一实现。
- 自动完成的等待时长是可配置的演示参数（演示值 30 秒左右，真实场景为分钟级）；之后改配置不影响已进入「待取餐」的订单。
- 自动完成不写取杯号：号是下单时定死的取餐凭证，「能否取餐／已完成」只由状态表达。

### 4.5 订单查询

**描述：** 用户只能读取自己的订单——这是数据归属在接口层的直接体现。列表与详情来自同一数据源，避免"列表和详情对不上"。本组实现 UJ-P2-1。

#### FR-P2-14: 我的订单列表

已登录用户可以分页读取自己的订单，按创建时间倒序。

**验收条件（可测）：**
- 结果只包含调用者本人的订单；他人订单在同一次调用中不可能出现。
- 排序为创建时间倒序；分页边界稳定（翻页过程中不重复、不遗漏已存在订单）。
- 返回结构与 Phase 1 的 `Order` 兼容，字段齐备：订单号 `id`、状态、就餐方式、商品摘要、金额与包装费、备注、取杯号、创建时间。
- 未登录请求被拒绝，而不是返回空列表。

#### FR-P2-15: 订单详情

已登录用户可以读取本人订单的完整信息。

**验收条件（可测）：**
- 只能读取本人订单；访问他人订单标识时被拒绝，且拒绝方式不泄露该订单是否存在。
- 详情包含商品明细（含快照与数量）、门店信息（名称、地址、电话）、订单号、下单时间、就餐方式、备注与金额，与列表展示保持一致。
- 详情与列表读取自同一数据源，不存在两套口径。

### 4.6 数据交付与安全基线

**描述：** 本组不是面向用户的功能，而是本阶段必须交付的工程质量基线：数据库可被任何人从零重建、类型由结构生成并入仓、数据访问策略默认拒绝、关键边界有测试证明。这四项正是 Phase 2 想向面试官展示的核心内容。

#### FR-P2-16: 迁移与种子数据（可复现重建）

项目的全部数据库结构、初始目录数据与对象存储配置以可重复执行的形式入仓（图片对象入仓不在本阶段交付，见修订记录）。

**验收条件（可测）：**
- 全部结构变更以迁移文件形式存在，不存在任何"只在控制台手工点过"的结构。
- 种子数据覆盖目录类数据：分类、商品（含可售状态）、规格组与选项、门店（商品图片引用不在本阶段交付，见修订记录）。**不包含订单**——订单只能由真实下单产生。
  - 这意味着全新用户的首屏订单列表是空的。Phase 1 靠预置的三状态 Mock 订单演示界面差异；Phase 2 起这三个状态由真实流程产生（下单 → 15 秒后「待取餐」→ 确认取杯「已完成」），演示自足。
- 对象存储的桶与读取策略以**声明式**方式入仓（迁移 SQL 或 config.toml + seed 任一）——图片对象入仓经 ly 裁定不在本阶段交付（见修订记录）。
- 在一个干净环境上，从零重建出与声明一致的结构、目录数据**不需要任何手工步骤**（不点控制台、不执行未入仓的 SQL；图片对象入仓不在本阶段交付，见修订记录）。
- 重建后的数据库可立即用于登录、下单与订单查询（不需要额外修补）。

#### FR-P2-17: 类型契约

数据库结构可生成 TypeScript 类型并纳入版本管理，作为服务端返回与客户端消费的形状来源。

**验收条件（可测）：**
- 类型可从当前数据库结构生成，生成物入仓；重新生成不需要任何手工修改。
- 结构变更后重新生成即可反映变化，生成过程不需要人工编辑。
- 服务端返回的字段与生成类型一致（含可空性），不出现"类型说有、实际没有"的字段。
- 对快照类字段（规格选择、门店快照等结构化副本）明确标注为需要手工类型覆盖的 JSON 结构，不假装生成类型能给出它们的精确形状。
- **Phase 2 不承诺客户端的编译期保护**：客户端消费这些类型时的类型安全取决于 Phase 3 选定的调用方式，该项属于 Phase 3 的验收，不作为 Phase 2 的完成条件。

#### FR-P2-18: 数据访问策略（RLS）

数据库启用行级访问控制，默认拒绝，按数据归属逐项开放。

**验收条件（可测）：**
- 所有对外暴露的表都启用了数据访问策略，且默认拒绝未授权的访问。
- 目录类数据允许公开读取；订单与订单明细只允许本人读取。
- **订单写入路径不对客户端开放**：已登录用户没有订单与订单明细的直接写入授权，写入只能经由服务端函数完成（与 FR-P2-9 一致）。
- 未认证请求无法读取任何订单数据。
- 拥有绕过策略权限的**服务端密钥不出现在客户端**（小程序包、客户端源码、客户端可读配置中均不得存在）。
- 有人（包括拿到发布密钥的人）直接绕过应用访问数据库时：读不到他人的订单，也无法自行写入一张金额自定的订单。

#### FR-P2-19: 后端测试基线

关键边界有可重复运行的测试证明。

**验收条件（可测）：**
- 测试覆盖三类边界：他人数据不可见、他人数据不可写、未认证不可读。
- 测试覆盖关键业务函数：下单金额以重算结果为准（客户端传入金额被忽略、归属取自会话）、非法状态迁移被拒绝、推进重复执行幂等。
- 测试可在本地以一条命令运行，失败时能定位到具体策略或函数。
- 测试在重建后的空库上可直接运行通过（不依赖手工准备的数据）。
- **测试范围的边界**：并发条件下的行为与真机链路（登录、会话续期）不在数据库层测试范围内——它们以"实现方式说明 + 人工验证记录"作为证据，不以自动化测试为完成条件（见 §11 反指标 SM-C3 的例外类别）。

**本组说明：** 不做种子数据完整性校验，不做面向接口的端到端自动化测试（见 §9）。

## 5. 跨切面 NFR

- **性能**：读取类请求（目录、订单列表、订单详情）的服务端处理时间目标为数百毫秒内（以本地实例的实测为准，本阶段不设 SLA 数值）；订单列表分页默认 20 条，避免一次拉全量。不出现随数据增长线性变慢的实现（例如无分页的全表扫描）。
- **可靠性**：任何写操作失败都不得留下中间态（订单与明细同事务、状态迁移以原子更新完成）。推进机制的一次失败不应导致订单永久卡在「制作中」——读取时的判定与周期性兜底共同保证。
- **可观测性**：错误必须可区分、可定位——登录失败、下单校验失败、状态迁移被拒各自对应明确的**错误类别枚举**，而不是统一的"服务器错误"（错误类别与微信错误码的映射见 docs/phase-2/addendum.md §H）。关键失败（登录换取失败、下单被拒、推进异常）在服务端留下带错误类别与请求标识的记录；日志中不得出现 AppSecret 或服务端密钥。
- **安全基线**：最小权限原则；客户端只持有发布密钥；服务端密钥仅存在于服务端运行环境；传输全部走 HTTPS。
- **兼容性**：**以后端生成的类型为唯一形状基准**。Phase 3 的对接方式是让前端类型向生成类型对齐，而不是要求后端迁就 Phase 1 手工定义的类型；对接期允许加法型改动，不允许结构性返工（与 SM-3 一致）。

## 6. 约束与护栏

**范围护栏**

- Phase 2 对小程序侧的改动只包含登录链路与一个用于联调的最小验证入口（能发起登录并携带会话发一次受保护请求），其余页面保持 Mock 驱动。因此 §4 中所有关于"客户端"的验收条件，在 Phase 2 的验证点是**后端返回的形状与行为**；客户端的可观察行为在 Phase 3 兑现。
- 除本节列出的改动外，Phase 2 不修改小程序任何业务页面、不改变任何交互行为。

**平台约束（微信侧）**

- 微信小程序的可请求域名必须完成 ICP 备案；Supabase 的域名（`*.supabase.co` 与边缘函数域名）无法通过域名配置校验，因此**不可能被加入白名单**。
- 开发期有绕过手段（按可靠性排序：开发者工具不校验 → 真机/体验版打开调试 → 同一局域网 IP 直连），本阶段依赖它们完成联调与演示；具体手法见 docs/phase-2/addendum.md §H。
- 正式发布（体验版在未打开调试时、正式版）将强制域名校验，届时需要额外方案（备案域名反向代理或经平台云托管中转）。这属于 Phase 3 之后的课题，本阶段只需保证不被它阻塞。
- 换取 OpenID 的接口**不需要 IP 白名单**（白名单只约束获取平台访问凭证类接口）；但调用频率受限，超出后返回"频率超限"错误。
- AppSecret 只在生成时显示一次，丢失只能重置（重置会作废旧值）。

**平台约束（Supabase 侧）**

- 本阶段不上云、不使用任何云端实例；以下为将来上云时的已知平台约束。
- 免费版对边缘函数有运行时与内存上限，长时间运行的任务不可行；空闲项目会被暂停，需人工唤醒。
- 边缘函数运行在无持久化磁盘的环境中，不能依赖本地文件状态。
- 调度不支持"某事件发生后延时 N 秒执行一次"：周期任务的最小间隔可以做到秒级，但它是**周期**而非事件相对。因此推进采用"读取时判定 + 周期兜底"，不依赖事件相对调度。
- 周期任务的并发与单次时长有限，推进逻辑必须短小、幂等、可重跑。

**开发环境约束**

- 迁移的本地全量重建与数据库层测试依赖本机容器环境（Docker）；这是"可复现重建"（FR-P2-16）与"测试基线"（FR-P2-19）得以验证的前提。
- 本阶段不使用云端实例：真机联调与演示走同一局域网直连本地栈；将来上云时仍由同一套迁移保证结构一致（本阶段以两次干净重建一致作为等价证据）。

**数据与合规护栏**

- 只存储 OpenID 作为身份标识；不采集、不存储昵称、头像、手机号、位置等个人信息，因此不涉及个人信息保护的额外义务。
- 不接真实支付：不涉及商户资质、资金与发票相关合规；金额均为演示数据。
- 演示用数据不含真实顾客信息。

## 8. 风险与缓解

| 编号 | 风险 | 影响 | 缓解 |
|------|------|------|------|
| R-1 | **域名备案问题**：微信不允许配置未备案的境外域名 | 正式发布环境下小程序无法直连后端；演示必须依赖调试模式 | 约束与三条绕过手段见 §6；发布前再决策反向代理或云托管中转（Phase 3 之后） |
| R-2 | 免费版实例空闲被暂停（本阶段不上云，暂不适用；保留为将来风险） | 演示或联调时接口全部不可用 | 演示前唤醒实例；保留本地全量重建能力，随时可在本地复现（FR-P2-16） |
| R-3 | **AppSecret 丢失或泄露** | 丢失需重置并更新所有引用；泄露可被冒用调用接口 | 生成后立即存入密码管理工具；只存放在服务端密钥配置中，绝不进入客户端与仓库 |
| R-4 | 微信接口限流或凭证失效 | 登录失败率上升 | 登录频率天然很低（仅启动时）；按错误类别区分并可重试（FR-P2-1、FR-P2-5）；不在客户端缓存一次性凭证 |
| R-5 | 推进不可靠（任务失败或无人读取） | 订单卡在「制作中」，演示时会被看出破绽 | 双保险：读取时判定 + 周期兜底；推进幂等可重跑；取杯号在下单时已分配，推进失败不影响报号（FR-P2-11、FR-P2-19） |
| R-5b | 用户取餐后忘记点「确认取杯」 | 订单永远挂在「待取餐」，列表不反映真实进度 | 超时自动完成兜底：进入「待取餐」后经过配置时长由服务端自动完成（读时判定 + 并入现有扫描任务）；手动确认与自动完成共用同一迁移实现（FR-P2-13） |
| R-6 | 客户端实时订阅不可用 | Phase 3 的"后端主动推送"方案落空 | 已调研并决策：本阶段不做订阅，Phase 3 用轮询兜底（docs/phase-2/addendum.md §E） |
| R-7 | **后端经验不足导致范围失控** | 交付延期，或半成品反而暴露短板 | 严格以本 PRD 的 FR 与非目标为边界；宁可少做而每项都有测试证明；不引入本阶段未列出的技术栈 |
| R-8 | 环境间结构不一致（本阶段为两次干净重建之间；上云后为本地与云端） | 测试通过但环境间行为不同 | 结构只允许通过迁移变更（FR-P2-16）；不接受控制台手工改结构；本阶段以两次重建的迁移列表一致、库与声明零差异对照 |
| R-9 | **前置资产拿不到**（小程序主体或第二个微信号） | UJ-P2-1 与 SM-2、SM-4 的验证方式被迫降级 | 尽早确认前置资产（§7）；最坏情况下改为沙箱内两套身份验证，并在文档中如实记录降级 |

## 9. 明确的非目标

Phase 2 **不做**以下事项；任何一项被顺手纳入，都视为范围失控：

- **不做**真实微信支付与退款，也不建立支付记录实体；订单创建即视为已支付（演示性质）。`[ASSUMPTION]`
- **不做**购物车服务端化——购物车继续留在客户端本地存储，下单时一次性提交。
- **不做**多门店、门店切换、门店定位与营业时间管理。
- **不做**商家/店员后台界面（Phase 4 范围）。
- **不做**商品的增删改接口与图片上传路径（Phase 4 范围）；本阶段商品数据由种子数据与控制台维护。
- **不做**订单取消、退款、售后与客诉流程；订单状态机只有三个阶段。
- **不做**优惠券、会员、积分、折扣与任何营销能力。
- **不做**用户资料体系（昵称、头像、手机号绑定、收货地址）。
- **不做**搜索、推荐、排序策略与个性化。
- **不做**实时订阅（Realtime）——已决策推迟到 Phase 3 评估。
- **不做**面向接口的端到端自动化测试、性能压测与安全渗透测试。本阶段测试范围限定在数据库层（FR-P2-19）；唯一例外是登录换取的可构造错误分类，可以用受控输入注入断言（FR-P2-1）。
- **不做** CI/CD、生产部署与多环境（测试/预发/生产）治理。
- **不做**接口版本化与对外兼容承诺——接口只服务本项目。

## 10. MVP 范围

### 10.1 包含

- 静默登录：一次性凭证换取 OpenID、身份映射与用户建立、会话签发与自动续期、失败分类与提示。
- 目录读取：分类、商品（含可售状态）、规格组与规格选项、门店、商品图片（均为公开读取；图片对象入仓不在本阶段交付，见修订记录）。
- 下单：输入校验、服务端金额重算、订单号服务端生成、幂等防重（含用户绑定）、订单与明细同事务落库、完整订单快照。
- 状态流转：下单时分配取杯号（见 FR-P2-11）；服务端推进（制作中→待取餐；读取时判定 + 周期兜底）、催单加速、用户确认取杯（→已完成）、合法迁移与并发安全。
- 订单查询：本人订单列表（分页、倒序）、本人订单详情。
- 工程基线：结构与配置声明式入仓（含对象存储桶与策略、定时任务）、可复现重建、类型生成入仓、数据访问策略、后端测试基线。
- 用于登录联调的最小客户端验证入口（不属于 Phase 3 的正式对接）。

### 10.2 不包含

- 真实支付、购物车上云、多门店、商家后台、商品写接口、订单取消、营销能力、用户资料、搜索推荐、实时订阅、端到端测试与部署流水线——逐项理由见 §9。

## 11. 成功指标

Phase 2 是过渡阶段，**不单独对外演示**（对外展示从 Phase 3 联调完成后开始）。因此成功指标不按"演示效果"设定，而按"是否真的为 Phase 3 铺好了路"设定。

**主要指标**

- **SM-1：可复现重建。** 在一台干净机器上，从零重建出与声明一致的结构、目录数据与对象存储配置（图片对象入仓不在本阶段交付），无任何手工步骤。目标：一次成功，无补做操作；结构一致性以两次从零重建一致为等价证据（本阶段无云端实例）。验证 FR-P2-16。
- **SM-2：数据归属经证明。** 换一个身份就读不到前一个身份的订单；未登录读不到任何订单；客户端提交的金额不影响落库金额；客户端无法直接写入订单。目标：全部成立，且由可重复运行的测试给出证据。验证 FR-P2-9、FR-P2-14、FR-P2-15、FR-P2-18、FR-P2-19。

**次要指标**

- **SM-3：对接不推倒重建。** Phase 3 对接期间允许**加法型改动**——新增字段、新增可选参数、补一个查询，这些属于正常迭代，不计为失败。**不允许的是结构性返工**：重做数据模型、重写接口契约形状、改动数据归属关系（例如订单明细结构重做、目录与规格的关系换形状）。目标：结构性返工 0 次；加法型改动不限次数，但每处都能说清原因。验证 FR-P2-6、FR-P2-9、FR-P2-14、FR-P2-15、FR-P2-17。
- **SM-4：身份链路真机可用。** 在真机上完成"登录 → 会话 → 携带身份访问受保护数据"，且重启小程序后仍保持登录。目标：真机一次通过。验证 FR-P2-1 ~ FR-P2-4、FR-P2-18。

**反指标（不予优化）**

- **SM-C1：不以表数量、接口数量、边缘函数数量衡量进度。** 结构越精简越好；为不确定的未来需求（多门店、权限体系、营销）预留结构计为负项。
- **SM-C2：不以"看起来很专业"的复杂度换取能力。** 任何本阶段未列出的技术栈（消息队列、缓存层、微服务拆分等）一律不做；评价标准是"每项交付都能说清为什么需要"。
- **SM-C3：不以"演示时能跑通"替代"测试能证明"。** 手工验证通过但缺少测试覆盖的边界，视为未完成。
  - **例外类别（不适用该标准）**：真机链路（登录、会话续期）、并发行为、跨实例的结构一致性（本阶段为两次干净重建一致 + 库与声明零差异；上云后为本地与云端迁移列表对照）——这三类以"实现方式说明 + 人工验证记录"为证据形式，不要求自动化覆盖。除此之外的边界仍适用本指标。

## 12. 开放问题

1. **Phase 3 的对接顺序。** 登录、目录、下单、订单查询四条链路先接哪条？影响"最小验证入口"需要做到什么程度。→ 待 Phase 3 规划时决定。

**已关闭的开放问题：**

- 身份映射记录什么（记录映射建立时间与最近登录时间；不记录任何设备信息）——见架构 spine AD-24。
- 会话有效期取值（沿用平台默认值，不自定数值；静默登录使过期对用户不可见，故"演示不被打断 vs 凭证泄露风险"这个取舍不成立）——见架构 spine AD-14。
- 商品图片的读取形态（公开读桶；私有桶需签名链接，而签名会过期、URL 会进入订单快照与缓存）——见架构 spine AD-20。
- 状态推进时长（下单后 15 秒）与催单提前量（提前到「催单时刻 + 3 秒」，与原定时刻取较早者以保证幂等）——两项均为可配置的演示参数，见 FR-P2-11、FR-P2-12。
- 取杯号形态与并发（外形为字母前缀 + 四位数字 `A-0008`、前缀用尽后轮转、门店本地时区的当日唯一、并发以原子更新保证）——见 FR-P2-11。
- 门店电话是否入快照（纳入：Phase 1 的订单详情页本就展示它）——见 FR-P2-8、FR-P2-15。
