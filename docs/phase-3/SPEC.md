# We-Order Phase 3 — 前后端对接

## Why

Phase 1 的界面是真的、数据是假的；Phase 2 的数据是真的、小程序还没接上。Phase 3 把这条缝焊死：静默登录、目录、下单、订单查询四条链路全部切到 Phase 2 的真实后端，删除全部 Mock 与旧 `api/` 实现，让面试演示的每一跳都发生在真实网络上（CAP-1~14、18~19）。同时正面进攻一个平台约束——小程序没有原生 WebSocket——自适配 Supabase Realtime 作为挑战项（CAP-15~17），成功与否不阻塞交付。受众是面试官与演示者 Ly；本阶段是最终公开演示（Phase 4）之前的本地真实闭环，交付的不是新功能，而是**可验证的真实性**。

## Capabilities

- **CAP-1** 统一请求对接层
  - **intent:** 客户端所有后端访问（REST / RPC / 支付接口 / 订阅）经一条通道完成，自动携带凭据、统一归一错误，调用点不感知鉴权与错误细节。
  - **success:** 全仓无页面/Composable 直发请求；请求恒带发布密钥、按需带访问凭证；失败以统一 `AppError`（服务端类别 + 客户端类别）上浮；对接层不持有会话或业务状态。
- **CAP-2** 类型契约对齐与编译期保护
  - **intent:** 客户端形状与后端生成类型保持单一来源，形状错误在编译期暴露而非运行期崩溃。
  - **success:** 生成类型入仓、不手改、无需手工同步步骤；Phase 1 手工类型退休（快照 JSON 覆盖类型标注出处）；字段可空性与实际一致。
- **CAP-3** 存量清理与单一数据源
  - **intent:** 清掉 Mock 与旧实现，客户端只保留一条真实数据通路。
  - **success:** `weorder_orders` / `weorder_cart` / `weorder_checkout_intent` 在启动 gate 被清空；`src/mock/`、旧 `api/`、`pages/auth-check/` 与 `pages.json` 声明移除；无 Mock 回退开关；本地库可由迁移 + seed 重建。
- **CAP-4** 启动静默登录
  - **intent:** 每次启动无感确保一个可用身份，且不阻塞任何页面。
  - **success:** 冷启动无登录界面、无授权弹窗、不索取资料；有效会话直接复用；失败按类别提示并可重试、不产生半登录状态；目录未登录可读。
- **CAP-5** 会话持久化与自动续期
  - **intent:** 会话跨重启存活、过期自动续期，调用方无感。
  - **success:** 重启免登录；过期时并发请求只触发一次续期且全部成功（单飞）；续期失败自动重登（退避 + 尝试上限），不产生第二身份、不循环掉线。
- **CAP-6** 会话状态归属修正
  - **intent:** 关闭 Phase 2 的有期限偏离——会话与续期状态迁出对接层，恢复 P1 AD-1（对接层不持有运行时状态）。
  - **success:** 对接层可独立替换（验证矩阵 #10）；上层不出现 token、不暴露未登录；会话不进 Pinia；唯一读写者持有 `weorder_session`。
- **CAP-7** 目录读取切到真实数据
  - **intent:** 分类 / 商品 / 规格 / 门店改从后端读取，界面交互与 Phase 1 保持一致。
  - **success:** 双栏联动、规格计价等行为无回归；下架不返回、售罄保留并带状态；缺图色块占位不阻塞；未登录可读；加载失败有失败态与重试。
- **CAP-8** 支付接口（支付 → 创建订单）
  - **intent:** 客户端经唯一服务端入口一次完成「模拟支付 → 创建订单」，金额、订单号、取杯号与归属全部由服务端产出。
  - **success:** 绕过入口的客户端建单被拒；成功即返回订单号 + 取杯号并进入状态机；客户端提交不含金额；成功清购物车、失败保留；保留 loading 与成功反馈。
- **CAP-9** 支付接口幂等与失败恢复
  - **intent:** 支付失败、超时与重试绝不产生重复订单，也绝不丢购物车。
  - **success:** 同一结算意图在超时重试与杀进程重试后仍只产生一张订单；失败按类别可区分且停留可重试；无「已报成功但无订单」状态。
- **CAP-10** 订单列表（三态）
  - **intent:** 从服务端读取本人订单并按制作中 / 待取餐 / 已完成分组展示。
  - **success:** 三态分组与分页（20 条）正确；进入页面与手动刷新均触发读时推进；读取失败不展示任何订单数据、不以空列表伪装；空态有引导且不做无意义轮询；归属不可伪造。
- **CAP-11** 订单详情与「再来一单」
  - **intent:** 详情展示服务端快照（含制作中即可见的取杯号），「再来一单」按快照还原购物车。
  - **success:** 快照不受商品改名改价影响；再来一单替换购物车、按当前目录价计价；失效行丢弃并 toast「部分商品已失效」。
- **CAP-12** 轮询刷新订单状态
  - **intent:** 在订单可见页面以轮询让服务端推进可见，离开即停。
  - **success:** 到点后 ≤ 1 个轮询周期 + 1s 自动更新；页面隐藏停止、回前台立即刷新；失败静默重试 3 次后降级手动刷新；状态应用单调、旧响应不覆盖新状态。
- **CAP-13** 催单
  - **intent:** 用户可催单把推进时刻提前，界面即时反馈。
  - **success:** 催单后 ≤ 1 个轮询周期 + 3s 可见待取餐；重复催单不更早不延后不报错；非制作中无入口或被拒提示明确。
- **CAP-14** 确认取杯与自动完成
  - **intent:** 待取餐可确认取杯；不操作时由服务端超时自动完成。
  - **success:** 确认后立即完成；不操作约 30s 后自动完成且 ≤ 1 个轮询周期感知；已完成单可再次打开。
- **CAP-15** Realtime 订阅自适配（挑战项）
  - **intent:** 以小程序可用传输订阅本人订单变化，让状态更新自己找上门（UJ-P3-2）。
  - **success:** 仅在有有效会话时建立；断线自动重连（退避 + 上限）、回退空窗 ≤ 2 个轮询周期；订阅更新与轮询共享同一单调应用路径；会话续期后凭证同步。
- **CAP-16** 订阅与轮询的切换与回退
  - **intent:** 订阅不可用时无感回退轮询，功能完整、不打扰用户。
  - **success:** 订阅建立失败 / 被拒 / 中途断开时自动回退（≤ 2 个轮询周期恢复更新），行为与纯轮询一致、无用户可见报错；不设统一开关。
- **CAP-17** Supabase 侧订阅配套
  - **intent:** 以最小加法型后端配置支撑订阅，并证明不泄露他人数据。
  - **success:** publication 只含 `orders`；A 订阅时 B 的订单变更不产生任何事件（含列级数据）；REST/RPC 行为不变、pgTAP 全绿（含新增反向与正向断言）。
- **CAP-18** 全局错误拦截与用户可见提示
  - **intent:** 兑现 P1/P2 约定——所有失败归一为类别并映射为用户可行动的提示。
  - **success:** 归一表覆盖 RPC / 边缘函数 / 平台 auth / 客户端网络；类别 → 文案唯一函数按 `source` 分域且编译期穷尽；下单失败至少区分售罄 / 规格失效 / 不可售 / 权限；提示不含敏感信息；页面有失败态与重试。
- **CAP-19** 关键失败不产生脏状态
  - **intent:** 登录、建单与状态变更失败都可恢复，不留中间态。
  - **success:** 登录失败无半登录；建单失败不丢购物车、不重复；催单 / 取杯失败不改本地状态；每步失败有明确下一步；演示路径无特判后门或假数据兜底。

## Constraints

- **后端只读基线**：P2 契约与 pgTAP 基线不得失效；只允许加法型改动，目标零结构性返工（diff 可审计）；spine AD-12 记录的调用面调整与静态权限断言反转属有意例外。
- **界面基准**：交互结构沿用 Phase 1，替换只发生在数据层；本阶段界面增量仅限最小 UI 规范（错误提示 / 失败态 / 重试入口 / 空态 / 缺图占位 / 提交防重复）。
- **客户端接入**：不引 Supabase 官方 SDK 与社区适配库；通用 HTTP 库已选 alova（仅传输与页面请求状态）；唯一例外 = `@supabase/realtime-js` 的 transport 扩展点。
- **密钥边界**：客户端只持发布密钥与会话凭证；服务端密钥只在边缘函数环境；提示与日志不含密钥、OpenID、堆栈。
- **会话纪律**：启动即静默登录（显式修订 P2 AD-14 惰性条款）；会话唯一读写者为 `core/session`、不进 Pinia、不进 `api/`、续期单飞 + 主动续期；请求头构造只在 `core/transport`；key 沿用 `weorder_session`。
- **订单读取纪律**：订单读取只经服务端读取路径（读时推进），客户端不直读表；订阅为显式例外（RLS 过滤的变更事件），RLS 是唯一归属裁决。
- **下单纪律**：`pay-order` 是客户端创建订单唯一入口；`create_order` 客户端不可达（直呼 42501）；服务端重算金额、归属取自会话；客户端提交的金额或用户标识一律不接受。
- **数据纪律**：购物车不上云（纯本地，下单时一次性提交）；Mock / 本地订单 / 购物车 / 本地库均无保留价值，可整体清空并由迁移 + seed 重建。
- **演示环境**：Phase 3 演示以本地环境为主（开发者工具或局域网真机调试）；Phase 4 前 Supabase 保持本地实例、不上云；备案与正式发布不在本阶段；面向面试官的公开演示版（真机自助访问）归 Phase 4。
- **时间判定全在服务端**：演示参数（推进 15s / 催单提前 3s / 自动完成 30s、扫描 3s、轮询 5s）为可配置服务端参数，客户端不参与判定。
- **验证策略**：不做端到端自动化与 CI/CD；证据为手动验证矩阵（spine 13 场景模板）+ 少量纯函数单测；接受无自动化回归网的代价。
- **节奏与止损**：M1（对接层 → 登录 → 目录 → 支付接口 → 订单 / 轮询 / 错误提示）为 demo-critical；M2（Realtime）是一天级挑战——一天内未跑通即降级纯轮询、不再投入。
- **反指标**：不以实时炫技挤占核心联调；不以复杂度换能力（未列技术栈一律不做）；不用假数据或特判后门伪装链路可用。
- **错误类别纪律**：`order_error_code` 保留既有类别 + 归一兜底 `unknown`（加法型，随本阶段迁移入库）；订阅失败对用户静默、不产生数据库类别；其它新增失败类别先在客户端侧记录，积累多了再考虑入库。
- **依赖失败语义**：外部依赖失败必须翻译为稳定错误类别（生成类型为类别唯一来源），由客户端据类别决定提示。

## Non-goals

- 备案与正式发布、生产部署与多环境治理（公开演示版与发布策略归 Phase 4）。
- 购物车上云（明确不做，不是待定项）。
- 真实支付渠道接入、支付记录实体与支付状态机。
- 图片对象入仓与上传（演示图由 Ly 自备，缺图占位）。
- 报价接口（结算页金额为展示性本地计价）。
- 对外可访问的部署与自助体验 / 扫码（属 Phase 4 的公开演示版；本阶段以现场演示与替代证据为准）。
- 商家后台、多门店、营销、搜索推荐、用户资料、订单取消 / 退款（沿袭 P2 非目标）。
- 端到端自动化测试、CI/CD、性能压测与安全渗透测试。
- 结构性返工（不改数据模型、不改契约形状、不改归属关系）。
- 把 Realtime 订阅纳入演示验收（挑战项不阻塞完成）。
- 保留 Mock 数据源、Phase 2 最小验证入口、绕过支付接口的客户端建单路径。
- 售罄 / 下架的任何差异化处理（不置灰、不做售罄专属交互）；统一在 Phase 4 修改。

## Success signal

- **SM-1：** 在演示环境冷启动后，UJ-P3-1 一次走完：静默登录 → 真实目录 → 加购 → 支付建单 → 催单 → 待取餐 → 已完成 → 查看订单，全程真实数据、无人工补救（用户在 UI 上点重试不算补救）。
- **SM-2：** 对接期间零结构性返工，可由 diff 审计；次要可验收项：错误可控（无白屏 / 未捕获异常）、类型契约编译期生效、Phase 1 关键交互逐项无回归。

## Assumptions

- 微信凭证校验所需前置资产（可用小程序主体、第二微信号）仍可用（沿袭 Phase 2）。
