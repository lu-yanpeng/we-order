# PRD: We-Order 点餐小程序 — Phase 3 前后端对接

> **三分钟速读**（按需往下翻）
>
> - **这一阶段干什么**：把小程序从 Mock 数据源切到 Phase 2 的真实后端——登录、目录、下单、订单查询四条链路全部走通，删掉全部 Mock 数据与旧 `api/` 实现，形成真实闭环。
> - **最大的一块**：重建客户端的**请求对接层**（自建 HTTP 调用，不引入 supabase-js；请求库选型见 addendum §B）。旧 `api/` 代码整体删除后重新设计，会话状态从 `api/` 内迁出——这是 Phase 2 记录的有期限偏离，本阶段正式关闭。
> - **最险的一段**：支付接口——支付与创建订单一次完成。订单创建成功，演示基本就成了。
> - **挑战项**：自适配 Supabase Realtime（基于公开协议、`uni.connectSocket` 提供传输层）。**不作为演示验收内容**；轮询始终是保底。
> - **怎么算成功**：完整下单流程一次演完（制作中 → 催单 → 待取餐 → 已完成 → 查看订单），全程真实数据、无人工补救；对接期零结构性返工。
> - **明确不做**：备案与正式发布（Phase 4 完成后再说）、购物车上云、真实支付、端到端自动化测试与 CI/CD。

## 1. 愿景

Phase 1 的页面是真的，数据是假的；Phase 2 的数据是真的，页面还没接上。Phase 3 把这条缝焊死：用户打开小程序，看到的是数据库里的商品；下的单归属自己的身份、存在服务端；出餐进度由服务端推进，而不是本地定时器演的。

对面试场景而言，这一阶段交付的不是新功能，而是**可验证的真实性**——从静默登录到订单完成的每一跳都发生在真实网络上，且每一跳的失败都有体面的兜底。

这也是一次主动的能力拓展：小程序运行时没有浏览器 WebSocket，Supabase 官方 SDK 无法直接使用。本项目选择自建 HTTP 对接层（Phase 2 已定路线，不引入官方 SDK），并以此为基础尝试自适配 Supabase Realtime——它不承担演示职责，是能力边界的一次正面进攻。

## 2. 目标用户

### 2.1 要完成的工作（Jobs To Be Done）

- （演示者·功能性）我要在有限的面试时间里演完一条真实闭环，证明前后端都是我的。
- （演示者·信任性）我要在被追问"数据从哪来、属于谁"时，能指着真实请求与真实归属回答。
- （演示者·成长性）我要把"小程序没有原生 WebSocket"这个约束正面解决一次——哪怕最终回退轮询，过程本身就是我要的能力积累。
- （演示中扮演的顾客·功能性）打开即用：浏览真实菜单、下单、看到进度、取餐、回看订单——全程不感知登录与网络细节。

### 2.2 非用户（本阶段）

- **商家/运营**：后台属 Phase 4；本阶段没有任何写入目录的能力。
- **多门店场景**：不做门店切换，目录与订单仍单一门店（沿袭 Phase 2）。
- **正式发布用户**：本阶段不解备案与发布链路，交付环境是开发/演示环境。

### 2.3 关键旅程

- **UJ-P3-1. Ly 在面试里一单到底。**
  - **Persona + context：** Ly，求职者。演示环境为开发版小程序（真机或开发者工具），已打开调试模式绕过域名限制。
  - **Entry state：** 小程序冷启动；无登录界面（静默登录）；目录数据来自 Supabase。
  - **Path：**
    1. 启动即完成静默登录（已有有效会话则直接复用），全程无感；
    2. 浏览目录（真实分类/商品/规格），选规格加购，进入结算；
    3. 模拟支付 → 调用服务端支付接口完成「支付 → 创建订单」：金额由服务端重算、订单号与取杯号由服务端产出；
    4. 订单列表出现该单（制作中）；点催单，等到变为待取餐；
    5. 确认取杯（或等待自动完成）→ 已完成；
    6. 切到已完成列表，打开订单详情；
    7. （可选加分项）换一个身份登录，证明该单读不到——把"数据属于谁"演给面试官看。
  - **Climax：** 全流程真实数据一次走通；被追问"这单存在哪、凭什么只属于你"时，答案落在会话与数据访问策略上。
  - **Resolution：** 演示收尾；订单留在服务端，可再次查看。
  - **Edge case（演示风险点）：** 支付接口调用失败（超时/网络/被拒）——页面给出可区分的错误提示，购物车保留，重试不产生重复订单。

- **UJ-P3-2. Ly 自己验证订阅：状态变化自己找上门。**（**挑战项，非演示验收内容**）
  - **Persona + context：** Ly，在真机上打开订单详情页，不动手。
  - **Entry state：** 订单详情页可见；订阅已启用（有有效会话）。
  - **Path：** 详情页保持可见 → 到点时服务端推进状态 → 页面经由 Realtime 订阅收到变化并更新，而不是等到下一次轮询。
  - **Climax：** 亲眼看到"服务端说了算 + 客户端被动收到"。
  - **Resolution：** 观察到一次订阅驱动的更新后收尾；断开订阅场景下确认回退轮询仍可用。
  - **Edge case：** 订阅不可用或断线 → 自动回退轮询，页面行为与无订阅时一致，用户无感。

## 3. 术语表

本阶段新增或需要澄清的术语如下；其余术语（会话、访问凭证/刷新凭证、静默登录、订单快照、服务端金额重算、取杯号、推进时刻、错误类别、可售三态、生成类型等）以 Phase 2 PRD §3 为准，本文档不重复定义。

- **请求对接层（对接层）** —— 小程序端访问后端的唯一通道：统一发起 REST/RPC 调用，负责会话携带、错误归一与类型约束。按 P1 AD-1，它**不持有业务或会话运行时状态**；本阶段重建，旧实现整体删除。
- **生成类型** —— 由数据库结构生成、入仓的 TypeScript 类型；客户端类型的唯一形状基准（Phase 2 契约）。
- **轮询** —— 客户端按固定间隔重新读取订单状态，使服务端推进可见；始终可用的保底刷新机制。
- **Realtime 订阅（自适配）** —— 客户端基于 Supabase Realtime 公开协议、用 `uni.connectSocket` 提供传输层，订阅本人订单的状态变化。本阶段为挑战项。
- **发布配置（publication）** —— 数据库层启用变更发布的配置；Realtime 订阅的前置。
- **支付接口** —— 承载「支付 → 创建订单」完整流程的服务端接口（边缘函数）；本阶段支付为模拟实现，为未来服务端支付流程预留单一入口（接入真实支付的契约形态见 §12 开放问题 5）。
- **演示参数** —— 15 秒推进 / 催单提前至 3 秒 / 30 秒自动完成（沿袭 Phase 2），可配置，不代表真实门店节奏。
- **存量清理** —— 删除 Mock 数据源、旧 `api/` 实现与 Phase 2 的最小验证入口；本阶段不允许 Mock 与真实数据并存。

## 4. 功能需求

### 4.1 请求对接层与类型契约

**描述：** 客户端与后端之间重建唯一通道。对接层替代 Phase 1 的 Mock 数据源与 Phase 2 遗留的 `api/` 实现；旧代码整体删除后重新设计，会话状态不再居住在对接层内（P2 已记录的有期限偏离，本阶段修正）。该层只负责"怎么发请求、怎么带身份、怎么报错、怎么对类型"，不承载业务规则。本组实现 UJ-P3-1。

#### FR-P3-1: 统一请求对接层

客户端所有后端访问都经由单一对接层完成，不允许页面或 Composable 直接发起网络请求。

**验收条件（可测）：**
- REST/RPC 与**支付接口（边缘函数）**的调用都经由对接层完成，不允许页面或 Composable 直接发起网络请求；支付接口的会话携带、错误归一与幂等键转发遵循同一套规则。
- 每个请求自动携带平台公开密钥（`apikey`）与当前会话的访问凭证；服务端密钥绝不出现在客户端。
- 请求参数与返回形状（含可空性）与生成类型一致；调用方拿到的是类型化结果，而不是 `any`。
- 失败统一归一为**服务端错误类别（生成类型）+ 客户端错误类别**，由对接层产出，不在各调用点重复判断。
- 对接层不持有业务状态或会话状态；会话的持久化与续期住在独立模块（见 FR-P3-6）。
- 不引入 Supabase 官方 SDK 与社区适配库；允许通用 HTTP 库（候选与对比见 addendum §B），底层仍为 `uni.request`；选型留待架构阶段（Realtime 的传输例外见 §6 与开放问题 6）。

#### FR-P3-2: 类型契约对齐与编译期保护

客户端类型向后端生成类型对齐，使形状错误在编译期被发现（兑现 Phase 2 留给本阶段的验收项）。

**验收条件（可测）：**
- 生成类型重新生成不需要手工修改；客户端引用同一份生成物，不复制、不手改；跨子项目的同步方式（生成命令 + 手动同步，见 ADR-0001）在架构阶段给出可复现步骤。
- Phase 1 手工定义在 `types/` 的类型在本阶段退休：替换为生成类型或其窄别名；快照类 JSON 字段的手工覆盖类型单独保留并标注出处。
- 服务端返回值被消费时，字段可空性与实际一致（不出现"类型说有、实际没有"导致的运行期崩溃）。
- 对接期允许加法型改动；**不允许**要求后端迁就 Phase 1 的手工类型，也不允许结构性返工。

#### FR-P3-3: 存量清理与单一数据源

Mock 数据源、旧 `api/` 实现与 Phase 2 的最小验证入口全部移除，客户端只保留一条真实数据通路。

**验收条件（可测）：**
- 本地存储中的 Mock 订单数据与存量本地购物车被清空（存量条目引用 Mock 商品数据，无迁移价值）；界面不再可能读到任何 Mock 内容。
- 本地数据库数据可整体清空并由迁移 + seed 重建（ly 裁定：无保留数据）。
- 旧 `api/` 代码删除（不保留死代码）；其职责由重建的对接层承接，会话职责另行安置；Phase 2 的最小验证入口移除。
- 不存在任何"Mock 与真实数据并存"的开关或回退路径。

### 4.2 静默登录对接与会话管理

**描述：** 把 Phase 2 已交付的登录后端接进真实启动流程：每次启动确保有一个可用身份，全程不打扰用户。本组实现 UJ-P3-1。

#### FR-P3-4: 启动静默登录

小程序启动时静默完成登录（一次性凭证 → 服务端换取 OpenID → 建立会话），用户无感。

**验收条件（可测）：**
- 本阶段裁定：**启动即静默登录**（不采用 P2 AD-14 的惰性触发）；架构文档需显式修订 AD-14 的惰性条款，避免下游两边引用。
- 不出现登录界面、不索取任何用户资料、不依赖用户点击。
- 已有有效会话时直接复用，不重复登录。
- 登录失败按错误类别给出可区分提示并可重试（并发登录产生的可重试 `session_failed` 属自动重试类别）；重试不留下半登录状态（不产生孤儿用户、不残留不可用会话）；失败提示与重试入口有明确位置——启动不阻塞页面，界面形态见 FR-P3-18 的最小 UI 规范。
- 未登录不阻塞目录浏览（目录公开只读，沿袭 Phase 2）。

#### FR-P3-5: 会话持久化与自动续期

会话凭证持久化在客户端本地，过期时自动续期并对调用方透明。

**验收条件（可测）：**
- 应用重启后会话可恢复，不需要用户再次操作。
- 职责接缝：会话模块持有会话状态并提供取凭证/续期能力；对接层只持有"请求前取凭证、401 时调用续期并重放一次"的拦截逻辑，不持有会话状态（见 FR-P3-6）。
- 访问凭证过期时自动续期并重试原请求，调用方无感；不出现"同一操作先失败再成功"的可见抖动。
- **续期单飞**：同一时刻只允许一个续期在飞，其余请求等待并复用同一结果。
- 续期失败可回退到重新静默登录，且不产生第二个身份；续期请求发出后应用被杀导致新凭证丢失时同样回退重登；重登有退避与尝试上限，不出现反复掉线或循环重试。

#### FR-P3-6: 会话状态归属修正

会话与续期状态不再居住在 `api/` 对接层内，恢复 P1 AD-1（API 层不持有运行时状态）；Phase 2 记录的有期限偏离在本阶段关闭。

**验收条件（可测）：**
- 对接层可被独立替换而不需要携带会话上下文；验证方式以「注入伪会话的手动验证记录」为证据（见 §6 验证矩阵）。
- 会话状态的承载位置有唯一出处，且不通过导入 `api/` 的方式访问；承载形态不得进入 Pinia（除非显式修订 P2 AD-14）；本地存储 key 沿用 `weorder_session`；承载形态由架构阶段决定（见开放问题 3）。
- 上层（页面/Composable）不出现 token 一词；请求头构造只在对接层与会话模块内；不向上层暴露未登录状态。
- Phase 2 架构 spine 的偏离记录可随之关闭（下游文档更新由架构阶段承接）。

### 4.3 目录对接（只读）

**描述：** 商品目录从 Supabase 读取，替换 Mock；界面行为完全沿用 Phase 1。本组为 UJ-P3-1 提供下单所需的真实数据。

#### FR-P3-7: 目录读取切到真实数据

分类、商品、规格与门店信息从后端读取；可售状态由后端返回（下架不返回、售罄保留并带状态）。

**验收条件（可测）：**
- 双栏联动、规格定制、实时计价等交互行为与 Phase 1 一致（图片呈现除外，见下条）。
- 商品图片源从本地资源切换到对象存储；图片缺失或加载失败以默认占位（色块）呈现、不阻塞列表渲染，且不出现与商品不符的图片。本阶段不做图片对象入仓与上传（演示图片由 Ly 自行准备）。
- 下架商品不出现在读取结果中；售罄商品保留并随结果返回状态。本阶段不做售罄/下架的差异化置灰交互（Phase 1 客户端未实现；统一在支付被拒时以可行动文案呈现），差异化交互属 Phase 4。
- 目录读取未登录即可用。
- 加载失败有明确的失败态与重试入口，不白屏（失败态形态见 FR-P3-18 的最小 UI 规范）。

### 4.4 下单对接

**描述：** 结算到创建订单的完整真实链路，由**支付接口**（边缘函数承载）一次完成「支付 → 创建订单」。客户端只提交"商品 id + 规格选择 + 数量 + 备注 + 就餐方式"，金额、订单号、取杯号全部由服务端产出（沿袭 Phase 2）。**这是本阶段演示的最大风险段落**（见 UJ-P3-1 Edge case）。

#### FR-P3-8: 支付接口（支付 → 创建订单）

模拟支付完成后，客户端经服务端支付接口完成创建订单；成功后订单进入服务端状态机。

**验收条件（可测）：**
- 客户端不具备绕过支付接口的订单创建路径（直呼既有创建路径被拒绝）；支付接口是客户端创建订单的唯一入口。权限收紧的具体手段由架构裁定（开放问题 5）。
- 「支付 → 创建订单」由支付接口一次完成，客户端交互保持在一次操作内；接口语义为**创建成功才返回支付成功**。
- 支付接口必须要求有效会话（与登录函数的例外相反），不得关闭会话校验。
- 订单创建仍由既有服务端创建实现完成，不出现第二套金额计算、归属判定或写路径；归属仍取自会话身份，支付接口不得引入客户端可伪造的用户标识参数，不得以服务端密钥绕过归属判定，不得直接写订单表。
- 支付环节本阶段为模拟实现，为未来服务端支付流程预留**单一入口**；接入真实微信支付必然涉及预下单、客户端二次授权与异步回调（契约形态见开放问题 5），本阶段不承诺"客户端零改动"——可验收的承诺仅为"存在单一替换接缝"。
- 客户端提交不含任何金额字段。结算页展示金额为客户端按目录数据的本地计价（沿用 Phase 1，仅展示口径）；订单金额以服务端重算为准，创建成功后订单展示以服务端返回金额为准（本阶段目录数据静态，不做报价接口——见 §9）。
- 创建成功后获得订单号与取杯号（下单即分配，沿袭 Phase 2），并可在订单列表看到该单；支付成功后的行为沿袭 Phase 1（清空购物车、重置备注与就餐方式、成功反馈并跳转订单列表；支付过程保留 loading）。
- 下单成功后清空本地购物车；**下单失败保留购物车**，用户可直接重试。`[ASSUMPTION: 清空/保留的时机沿袭 Phase 1 行为]`
- 本阶段不接真实支付渠道、不建立支付记录实体与支付状态机（沿袭 Phase 2）。

#### FR-P3-9: 支付接口幂等与失败恢复

支付接口的失败与重试不会产生重复订单，也不会让用户丢单或丢购物车。

**验收条件（可测）：**
- 幂等键定义为**一次结算意图**：进入确认订单页时由客户端生成并持久化到本地存储；购物车内容或就餐方式变化即作废重建；下单成功或明确失败后清除，超时不明则保留。键为必填、与用户绑定，经对接层/支付接口原样转发（沿袭 Phase 2 AD-11）。
- 网络超时后的重试复用同一幂等键；服务端不会因重试产生第二张订单；**杀进程后重试仍不产生第二张订单**。
- 支付接口失败给出可区分的错误提示（网络 / 业务拒绝 / 鉴权失效；业务原因至少区分售罄、规格失效、商品不可售），并停留在可重试的界面状态。
- 接口内部失败不产生「已显示支付成功但没有订单」的不可恢复状态；失败后可安全重试。
- 失败路径结束后，购物车内容与失败前一致。

### 4.5 订单查询与状态流转对接

**描述：** 订单列表与详情从服务端读取（读取时由服务端推进状态），并以轮询作为默认刷新机制，使演示参数（15s / 3s / 30s）在界面上可见地推进。本组实现 UJ-P3-1。

#### FR-P3-10: 订单列表（三态）

订单列表从服务端读取，按制作中 / 待取餐 / 已完成分组展示，归属隔离由后端保证。

**验收条件（可测）：**
- 订单读取一律经**服务端读取路径（读时推进）**；客户端不直接读表，REST 裸表仅作纵深防御（沿袭 Phase 2 AD-5）。
- 三态分组与 Phase 1 一致；分页沿袭 Phase 2 默认（20 条）。
- 读取失败（未登录/会话失效）时先触发续期或重登：成功则继续展示本人订单；失败则显示失败态与重试入口，不展示任何订单数据（含本地缓存），不以空列表伪装成功；归属不可伪造（客户端不传用户标识）。
- 全新身份的空订单态有明确呈现（文案 + 引导去点餐）；空态不做无意义轮询。
- 进入页面与手动刷新均触发最新读取（读取即推进，保证状态不落后）。
- **展示增量（2026-09-26）**：订单卡片以商品图片行呈现商品（不再展示商品名与规格文字）；图片行只占一行，每个明细行一张图（同款同规格合并、不同规格分行），放不下的部分以渐变遮罩 + `+N` 标示未展示行数；缺图以色块占位。

#### FR-P3-11: 订单详情

订单详情展示服务端快照（商品、规格摘要、金额、门店信息、取杯号），"再来一单"按快照还原购物车。

**验收条件（可测）：**
- 详情字段与生成类型一致；快照字段即使商品已改名/改价也不变。
- 取杯号在制作中即展示（付款后即出号；沿袭 Phase 2「下单即分配」，属对 Phase 1 界面的有意增量）。
- "再来一单"沿用 Phase 1 行为（替换当前购物车、返回首页、自动展开面板），按服务端快照还原规格选择；购物车计价永远按当前目录价，快照价仅用于历史展示。
- 快照中商品已下架或规格已失效的行被丢弃，并以 toast 简单提示「部分商品已失效」（不阻断其余条目）；行为写入手动验证矩阵。
- **展示增量（2026-09-26）**：每条明细在名称前显示商品图片缩略图；名称与规格摘要照旧完整展示（一条不少）；缺图以色块占位。

#### FR-P3-12: 轮询刷新订单状态

在订单可见的页面上按固定间隔读取最新状态，使服务端推进（含催单与自动完成）及时可见。

**验收条件（可测）：**
- 制作中 / 待取餐状态下，推进时刻到点后页面在**不超过一个轮询周期 + 1 秒**内自动更新，不依赖用户手动刷新。
- 页面隐藏/离开时停止轮询，回到前台立即刷新一次（onHide/onShow 语义）。
- 轮询失败静默重试（默认 3 次）后降级为手动刷新入口，且不会造成请求堆积；失败提示与重试入口沿用 FR-P3-18 的规则。
- **状态应用单调**：轮询与订阅共享同一条状态应用路径，结果带请求序号，只接受不早于本地状态的结果，旧响应不得覆盖新状态。
- 轮询间隔取值必须满足上述可见性上界（数值由架构阶段定，见开放问题 1）。`[ASSUMPTION: 轮询在页面可见期间运行、离开即停]`

#### FR-P3-13: 催单

催单调用服务端把推进时刻提前（取原定时刻与"催单时刻 + 3 秒"的较早者），界面即时反馈。

**验收条件（可测）：**
- 催单后在一个轮询周期 + 3 秒（催单演示参数）内可见状态推进。
- 重复催单幂等：不会更早、不会延后、不报错。
- 非制作中状态的订单不出现催单入口，或催单被拒绝时提示明确。
- 制作中窗口有限（演示参数 15 秒），演示时可用配置临时调长推进时长以保证催单可演（演示剧本见 addendum §F）。

#### FR-P3-14: 确认取杯与自动完成

用户在待取餐状态可确认取杯；不确认时由服务端在等待时长后自动完成。

**验收条件（可测）：**
- 确认取杯后订单立即进入已完成。
- 不做任何操作的订单在演示参数（约 30 秒）后由服务端自动完成，页面在一个轮询周期内感知。
- 已完成订单在列表中归属"已完成"分组，详情可再次打开。

### 4.6 Realtime 实时更新（挑战项）

**描述：** 主动拓展能力边界：自适配 Supabase Realtime，使订单状态变化由服务端推送到客户端，替代默认轮询。**本组不作为演示验收内容；轮询始终是可用保底。** 本组实现 UJ-P3-2。

#### FR-P3-15: Realtime 订阅自适配

客户端基于 Supabase Realtime 公开协议、以 `uni.connectSocket` 提供传输层，订阅本人订单的状态变化。

**验收条件（可测）：**
- 订阅仅在有有效会话时建立；会话续期后订阅所用凭证同步更新。
- 断线自动重连并恢复订阅，采用退避策略与重试上限（不产生重连风暴）；订阅断开到回退轮询生效的空窗不超过 2 个轮询周期。
- 订阅收到的状态变化与轮询共享同一条状态应用路径（单调应用，见 FR-P3-12）；订阅建立成功后的轮询策略（降频或停止）由架构定，但不得出现双倍刷新或旧结果回写。
- 实现路线二选一并在架构阶段收敛（开放问题 6）：单独使用 `@supabase/realtime-js` 的传输扩展点（视为 §6 约束的显式例外），或零 SDK 手写协议客户端；两者都不依赖已停更的社区适配库。`[ASSUMPTION: 订阅对象为本人订单的状态变化]`

#### FR-P3-16: 订阅与轮询的切换与回退

订阅不可用时自动回退轮询，用户无感；不设统一开关（验证纯轮询行为时临时调整代码）。

**验收条件（可测）：**
- 订阅不可用时，全部刷新行为与 FR-P3-12 一致（功能完整）。
- 订阅建立失败、被拒绝或中途断开时，自动回退轮询（≤ 2 个轮询周期内恢复更新）；页面行为不降级、不报错打扰用户。
- 回退与恢复过程在开发期可观察，但不面向用户暴露。

#### FR-P3-17: Supabase 侧订阅配套

后端补上订阅所需的最小配置与验证，仅做加法型改动。

**验收条件（可测）：**
- 发布配置（publication）启用，覆盖范围（表/列清单）在架构阶段列明，仅限订阅所需最小集合。
- 数据访问策略与订阅兼容的验证方式：两个身份客户端，A 订阅、B 产生订单变更——A 收不到任何事件（含列级数据）；`orders` 的本人 SELECT 策略是订阅前置。以人工验证记录为证据（见 §6 验证矩阵）。
- 现有 REST/RPC 行为不受影响；类型契约向后兼容（加法型改动）；P2 的数据库测试基线（pgTAP）保持可运行且通过。权限收紧（服务端包装函数）带来的既有用例调用身份调整与静态权限断言反转属架构阶段的有意修订，不视为「使既有断言失效」；另新增反向（直呼被拒）与正向（身份注入生效）断言。

### 4.7 错误处理与用户提示

**描述：** 兑现 Phase 1 架构约定（"全局错误处理在 Phase 3 引入"）与 Phase 2 的交付边界（"Phase 2 只交付类别与映射，界面属于 Phase 3"）。本组实现 UJ-P3-1。

#### FR-P3-18: 全局错误拦截与用户可见提示

所有后端请求失败经统一拦截，归一为错误类别并映射为用户可见提示。

**验收条件（可测）：**
- 错误类别为**服务端生成类别 + 客户端类别**的联合：纯客户端失败（网络不可达 / 超时 / 请求取消 / 会话失效）有明确的客户端类别集合；类别到文案的翻译只有一个函数，同时消费两类。
- 服务端类别在响应中的承载字段由架构阶段与 Phase 2 侧核对并钉死（必要时为加法型改动）。
- 支付接口的类别复用 `order_error_code`，未知类别归一为加法型 `unknown`（保留；随本阶段迁移入库并重新生成类型）；订阅失败对用户静默、不产生数据库类别；其它新增失败类别先在客户端侧记录，积累多了再考虑入库。类别取值仍以生成类型为唯一来源。
- 下单失败至少区分：售罄、规格失效、商品不可售、权限等业务原因，提示文案可行动。
- 提示不包含内部堆栈、数据库细节、密钥或 OpenID 等敏感信息。
- 页面级加载失败有失败态与重试入口；操作级失败不留下脏界面（如可重复点击的提交按钮）。
- 本组是对 P1 AD-7『不建全局错误拦截器』的**显式替代**；Phase 1 未覆盖的界面增量（错误提示、失败态、重试入口、空态、缺图占位、提交防重复态）在本阶段首次定义，形态与文案来源由架构阶段的最小 UI 规范落定（开放问题 8）。

#### FR-P3-19: 关键失败不产生脏状态

演示路径上的关键失败（登录、创建订单、状态变更）都不产生难以恢复的中间态。

**验收条件（可测）：**
- 登录失败不产生半登录状态；创建订单失败不丢购物车、不产生重复订单；催单/确认取杯失败不改变本地展示的状态。
- 任一步失败后，用户都能在界面上找到明确的下一步（重试/返回）。
- 演示路径不依赖任何"特判后门"或假数据兜底（与反指标 SM-C3 一致）。

## 5. 跨切面 NFR

- **性能**：目录加载与下单路径在演示网络条件下不出现可感知卡顿（以演示预演记录为证据）；轮询不得造成请求堆积或界面卡顿（离开即停、同一时间单实例）。
- **可靠性**：写路径幂等（至少覆盖创建订单）；读路径失败可重试；订单状态推进不依赖客户端在线（沿袭 Phase 2）。
- **安全**：客户端只持有可公开的发布密钥与会话凭证；服务端密钥绝不出现；提示与日志不含敏感信息；订阅不泄露非本人数据。
- **兼容性**：不引入 Supabase 官方 SDK 与社区适配库（Realtime 传输例外见 §6）；界面结构与交互沿用 Phase 1 基准，替换只发生在数据层；结算栏分包按需加载（P1 AD-4）不回归；本阶段首次定义的界面增量以 FR-P3-18 的最小 UI 规范为准。
- **可观测性（开发期）**：订阅连接、回退与重连过程可在开发期被观察；错误类别贯穿到用户提示。

## 6. 约束与护栏

- **平台约束**：小程序无 `fetch`/原生 WebSocket；请求域名需备案。**后端环境：Phase 4 前 Supabase 保持本地实例、不上云**；Phase 3 演示以本地环境为主（开发者工具或同一局域网真机调试，沿袭 P2 修订）。**备案与正式发布不在本阶段**；面向面试官的公开演示版（真机自助访问）归 Phase 4。演示栈预检与演示剧本见 addendum §F。
- **对接纪律**：以后端生成类型为唯一形状基准；只允许加法型改动，**不允许结构性返工**（沿袭 Phase 2 SM-3，本阶段目标 0 次）；P2 的数据库测试基线（pgTAP）保持跑绿。
- **数据纪律**：Mock 数据、本地购物车、本地数据库数据均可整体清空（ly 裁定：无保留数据）；**不做购物车上云**——购物车继续留在客户端本地存储，下单时一次性提交（沿袭 Phase 2）。
- **客户端接入**：不引入 Supabase 官方 SDK 与社区适配库；允许通用 HTTP 库（候选见 addendum §B），底层仍为 `uni.request`（Phase 2 附录 §G 已定路线）。Realtime 的实现路线二选一（realtime-js 仅用 transport 扩展点 / 手写协议客户端），由开放问题 6 收敛；如采用前者，视为对本条约束的显式例外。
- **订单读取纪律**：订单读取一律经服务端读取路径（读时推进）；客户端不直接读表（沿袭 Phase 2 AD-5）。
- **支付纪律**：支付接口是客户端创建订单的唯一入口（客户端直呼被拒）；本阶段为模拟支付、不建立支付记录实体（沿袭 Phase 2）；接缝形态见 FR-P3-8 与开放问题 5。
- **验证策略（ly 裁定）**：不做端到端自动化测试、不做 CI/CD；作为交换，交付一份**手动验证矩阵**（场景 × 期望 × 实际 × 证据），覆盖演示路径与主要失败场景（含登录失败、续期单飞、杀进程后重试、订阅回退）；允许对纯函数做少量单元测试（错误映射、状态映射、幂等键管理）。**接受无自动化回归网的代价**，以矩阵记录作为证据形式；架构文档给出清单模板。
- **会话状态纪律**：会话状态不居住在对接层；续期单飞；不上浮（上层不见 token、不暴露未登录状态）；不进 Pinia；key 沿用 `weorder_session`（FR-P3-5/6，承载位置见开放问题 3）。
- **实施节奏与止损**：M1（demo-critical）= 对接层 → 登录 → 目录 → 支付接口（模拟）→ 订单/轮询/催单/确认 → 错误提示，达成 SM-1；M2（加分）= Realtime 挑战，止损线：PoC 超过 1 天（Ly 裁定，与 AI 协同）或演示前仍未跑通，即降级为纯轮询、不再投入。

| 支付接口（新增边缘函数） | 支付 → 创建订单 | 按错误类别提示并可重试；不产生重复订单 | 本阶段模拟支付；客户端创建订单的唯一入口（FR-P3-8） |
| Supabase Realtime | 订单状态订阅（挑战项） | 自动回退轮询 | 需补 publication 配置与 RLS 兼容性验证（FR-P3-17） |
| 本地演示栈（Docker / 本地 Supabase / 边缘函数运行时 / 局域网可达） | 演示运行环境 | 演示前预检（addendum §F）；不可用时以录屏/截图作为替代证据 | Phase 4 前不上云 |
| Phase 1 界面基准 | 交互行为的唯一参考 | —— | 本阶段不改交互结构，只换数据源（界面增量见 FR-P3-18） |

**依赖原则：** 外部失败必须被翻译成稳定错误类别（Phase 2 已定义并生成到客户端），由客户端据类别决定如何提示；本阶段补齐"提示界面"这一半。

## 8. 风险与缓解

| 编号 | 风险 | 影响 | 缓解 |
|------|------|------|------|
| R-1 | 支付接口失败（网络超时/被拒）——用户点名的最险段落 | 演示中断、可能丢购物车或产生重复单 | 幂等键 + 错误类别提示 + 保留购物车 + 安全重试（FR-P3-8/9/18） |
| R-2 | 静默登录在真机/演示环境失败 | 下单链路整体不可用 | 错误分类提示、可重试、目录仍可浏览；已有有效会话直接复用（FR-P3-4/5） |
| R-3 | Realtime 自适配超预算或失败 | 挑战项无产出 | 轮询始终可用；订阅为增量、随时可退（FR-P3-12/16）；不纳入演示验收 |
| R-4 | 域名白名单/调试模式在演示设备上失效 | 演示无法进行 | 开发者工具不校验、真机调试模式、局域网 IP 直连三条路（沿袭 Phase 2 附录 §H） |
| R-5 | 轮询过密造成请求堆积或界面卡顿 | 体验与演示稳定性 | 间隔控制、离开即停、单实例、失败不叠加（FR-P3-12） |
| R-6 | 类型不一致导致运行期错误 | 局部崩溃、白屏 | 生成类型对齐 + 编译期保护 + 手动真机覆盖（FR-P3-2） |
| R-7 | 会话续期失败打断演示 | 中途要求重新登录 | 自动重登兜底；失败按类别提示（FR-P3-5/18） |
| R-8 | 客户端数据层重写的隐藏工作量（对接层 + 会话 + 支付接口 + 轮询） | 演示窗口内做不完 | M1/M2 里程碑与止损（§6）；Realtime 超预算即降级纯轮询 |
| R-9 | 本地演示栈 / 局域网在演示日不可用 | 演示无法进行 | addendum §F 预检清单；备用证据（录屏/截图） |

## 9. 明确的非目标

- **不做**备案与正式发布链路——Phase 3 演示以本地环境为主（开发版/调试模式）；面向面试官的公开演示版（真机自助访问）归 Phase 4。
- **不做**购物车上云——购物车继续纯本地（已确认，不是待定项）。
- **不做**真实支付渠道接入——本阶段支付接口为模拟实现、订单创建即视为已支付（沿袭 Phase 2）；接缝为真实微信支付预留，但接入不在本阶段。
- **不做**图片对象入仓与上传——演示图片由 Ly 自行准备，缺图以占位（色块）呈现。
- **不做**报价接口——结算页金额为展示性本地计价，订单金额以服务端重算为准。
- **不做**对外可访问的部署与自助体验（面试自助扫码属 Phase 4 的公开演示版；本阶段以现场演示与替代证据为准）。
- **不做**商家后台、多门店、营销能力、搜索推荐、用户资料、订单取消/退款——沿袭 Phase 2 非目标（商家后台属 Phase 4）。
- **不做**面向接口的端到端自动化测试、CI/CD、生产部署与多环境治理（ly 裁定，见 §6 验证策略）。
- **不做**性能压测、并发压力测试与安全渗透测试。
- **不做**结构性返工：不改动 Phase 2 数据模型、不重写接口契约形状、不改数据归属关系。
- **不把** Realtime 订阅纳入演示验收内容——它是挑战项，成功与否不阻塞本阶段完成。
- **不保留** Phase 1 的 Mock 数据源与 Phase 2 的最小验证入口。
- **不保留**绕过支付接口的客户端创建订单路径（权限收紧，见 FR-P3-8）。

## 11. 成功指标

**主要**

- **SM-1：演示一次通过。** UJ-P3-1 的完整流程（下单 → 催单 → 待取餐 → 已完成 → 查看订单）在真机（或开发者工具）上一次走完，无人工补救；定义：「人工补救 = 手工改库 / 重启服务 / 使用假数据；用户在 UI 上点重试不算」。验证 FR-P3-4/5/7/8/10 ~ FR-P3-14/18 的成功路径。
- **SM-2：零结构性返工。** 对接期间的迁移与类型变更全部为加法型，可由 diff 审计（无表结构重做、无契约形状变更、无归属关系改动）；每次契约改动有记录与理由。验证 FR-P3-2。

**次要**

- **SM-3：错误可控。** 演示路径上的失败均以可区分的错误类别提示呈现，无未捕获异常、无白屏。验证 FR-P3-18、FR-P3-19。
- **SM-4：类型契约生效。** 客户端类型与生成类型对齐，形状错误在编译期暴露。验证 FR-P3-2。
- **SM-5（挑战）：Realtime 自适配跑通。** 本人可观察到一次订阅驱动的状态更新，且订阅断开后回退轮询可用。验证 FR-P3-15 ~ FR-P3-17。**不作为本阶段完成的阻塞条件。**
- **SM-6：界面无回归。** 数据源替换后，Phase 1 关键交互（目录双栏联动、规格计价、购物车、结算、支付成功后续、列表/详情/再来一单）逐项复验通过；图片以占位呈现。验证 FR-P3-7/11；证据：手动验证矩阵。

**反指标（不要优化）**

- **SM-C1：不以实时炫技挤占核心联调。** 订阅失败不得阻塞其余交付，回退轮询必须始终可用。平衡 SM-5。
- **SM-C2：不以"看起来专业"的复杂度换取能力。** 未列出的技术栈一律不做（请求库选型与 Realtime 传输例外见 §6 / addendum §B）；每项交付都能说清为什么需要（沿袭 Phase 2）。
- **SM-C3：不用假数据或特判后门伪装链路可用。** 演示与验收中的可见数据必须来自真实后端。平衡 SM-1。

## 12. 开放问题

1. **轮询间隔取值。** 必须满足 FR-P3-12 的可见性上界（到点后 ≤ 一个轮询周期 + 1 秒可见）；具体数值待架构阶段决定。
2. **Realtime"跑通"的验收线。** 建议线：本人可观察到一次订阅驱动的状态更新 + 断开后 ≤ 2 个轮询周期内回退可用；架构阶段细化。
3. **会话状态承载位置。** P1 AD-1 恢复后，会话与续期状态住在哪里、以什么形态存在——待架构阶段决定；不得进入 Pinia，key 沿用 `weorder_session`（FR-P3-6）。
4. **演示环境最终形态。** 开发者工具还是真机开发版为主——演示前决定。
5. **支付接口与既有创建路径的身份传递方式**（转发调用者会话 / 服务端密钥 + 会话声明注入等），以及客户端直呼被拒的强制手段——需在 P2 AD-2/AD-3 的约束下由架构阶段裁定（FR-P3-8）。
6. **Realtime 实现路线二选一**：`@supabase/realtime-js` 仅用 transport 扩展点（§6 约束的显式例外），或零 SDK 手写协议客户端——架构阶段收敛。
7. **错误类别的传输承载字段与客户端类别集合**：与 Phase 2 实现/文档核对后钉死（可能的加法型改动，FR-P3-18）。
8. **最小 UI 规范**：错误提示、失败态、重试入口、空态、缺图占位、提交防重复态的形态与文案来源——架构阶段产出，作为 FR-P3-18 / FR-P3-7 的验收基准。

以上开放问题均不阻塞本 PRD 定稿：由架构阶段（或演示前）给出结论；其中 1 与 6 直接影响演示可测性与 §6 的约束例外，建议优先收敛。

**2026-09-25 收敛状态：** 1/3/5/6/7/8 已由 Phase 3 spine 收敛（轮询 5s；会话入 `core/session`；`pay-order` + `create_order_for_user`；realtime-js transport 扩展点；错误域分派 + `AppError`；最小 UI 规范）；2 按建议验收线执行、时间盒 1 天（Ly 裁定）；4 定为本地演示为主（工具形态演示前选），公开演示版归 Phase 4。
