## 设计思路：侧边栏 ↔ 商品列表双向联动

### 问题
侧边栏选中某个分类 → 商品列表自动滚到对应区域；反过来，手指滑动商品列表 → 侧边栏高亮也要跟着变。两个方向的联动都要"丝滑"。

### 方向一：侧边栏点击 → 列表滚动

这个方向相对简单。微信 scroll-view 组件提供了 `scroll-into-view` 属性：传入一个元素 id，组件自动滚动到该元素（对齐滚动区顶部）。

```html
<scroll-view :scroll-into-view="scrollIntoViewId" ...>
  <view id="section-coffee">...</view>
  <view id="section-tea">...</view>
</scroll-view>
```

**关键坑 1**：如果两次设置同一个 id，scroll-view 不会重复滚动。所以需要"先清空再赋值"：

```ts
scrollIntoViewId.value = ''          // 先清空
nextTick(() => {
  scrollIntoViewId.value = categoryId // 再赋值，值变了才触发滚动
})
```

**关键坑 2**：`scroll-into-view` 触发的滚动过程中，scroll-view 会发射 `@scroll` 事件，这个事件如果被"方向二"的处理器捕获，会把侧边栏高亮改回去，造成"回弹"效果。

解决方案：**目标锁**。点击时记录目标分类及其预算 top，程序化动画期间左侧高亮钉在点击目标上；只有「滚动真正到达目标附近」或「用户手指接管列表」才解锁：

```ts
let programmaticTarget: { id: string; top: number } | null = null

const handleSidebarClick = (categoryId) => {
  activeCategory.value = categoryId
  const top = sectionPositions.value.find((p) => p.id === categoryId)?.top
  // 位置尚未测量时退化为无锁，由右侧滚动的常规匹配兜底
  programmaticTarget = top === undefined ? null : { id: categoryId, top }
  scrollIntoViewId.value = ''
  nextTick(() => { scrollIntoViewId.value = anchorId(categoryId) })
}

const handleContentScroll = (e) => {
  const { scrollTop } = e.detail
  if (programmaticTarget) {
    // 还没到目标：高亮保持点击项，右→左不参与
    if (scrollTop + BOUNDARY_TOLERANCE_PX < programmaticTarget.top) return
    programmaticTarget = null // 到达（或越过）目标，解锁
  }
  // ...方向二的常规匹配...
}

// 用户手指碰列表 = 立即解锁（安全网，见下方说明）；模板上绑定 @touchstart
const handleContentTouchStart = () => { programmaticTarget = null }
```

> 注：微信 scroll-view 在执行 `scroll-into-view` 平滑动画期间通常不接受用户拖拽（滚动由动画掌控，打不断）。因此 `@touchstart` 的作用不是"打断动画"，而是**安全网**：当真机落点残差大于容差、目标锁无法因"到达"而释放时，用户一碰列表即可恢复右→左联动，避免高亮被永久锁死。

> ⚠️ 不要用「布尔标志 + 固定时长 setTimeout（如 400ms）解锁」。`scroll-into-view` 的动画时长与定时器同量级，末尾 scroll 事件早到/晚到决定它是否被锁挡掉，会让同一次操作时对时错——2026-10-06 的"高亮回退一位"就是这么来的，详见文末《复盘》。

### 方向二：列表滚动 → 侧边栏高亮

这个方向更难。核心思路：**预计算每个分类区块在滚动内容中的 top 坐标，滚动时用 scrollTop 对比这些坐标，找出当前处于顶部的分类。**

#### 1. 预计算坐标

```ts
const query = uni.createSelectorQuery()
query.select('.content-area').boundingClientRect()  // A: scroll-view 自身
query.select('#section-coffee').boundingClientRect() // B1: 分类1区块
query.select('#section-tea').boundingClientRect()    // B2: 分类2区块
// ... 每个分类一个
query.exec((res) => {
  const scrollViewTop = res[0].top       // scroll-view 在页面中的 Y 坐标
  sectionPositions = categories.map((cat, i) => ({
    id: cat.id,
    top: res[i + 1].top - scrollViewTop  // 区块 top 减去 scroll-view 的 top
  }))                                    // = 区块在滚动内容中的相对位置
})
```

`boundingClientRect().top` 返回的是元素相对于**页面视口**的 Y 坐标，不是相对于 scroll-view 内容的坐标。所以需要减去 scroll-view 自身视口的 top，才能得到正确的位置。

**为什么在 `onMounted` + `setTimeout(400ms)` 中执行？** 确保 DOM 渲染完成、布局计算完毕，否则 `boundingClientRect` 返回的坐标可能不准确。

#### 2. 滚动时判断

```ts
const handleContentScroll = (e) => {
  const { scrollTop } = e.detail  // 当前滚动偏移量
  for (let i = positions.length - 1; i >= 0; i--) {
    if (scrollTop + BOUNDARY_TOLERANCE_PX >= positions[i].top) {
      activeCategory = positions[i].id  // 命中：当前处于第 i 个分类
      return
    }
  }
}
```

从后往前遍历，第一个满足 `scrollTop + 容差 >= 该分类top` 的就是当前可见的分类。

**为什么不直接严格比较、要 +1px 容差？** `@scroll` 事件的 `scrollTop` 是 float32 精度，而 `boundingClientRect` 预算出的 top 是 double。实测：目标 top=6020.8（double），事件给出 6020.7998046875（float32 向下偏约 0.0002px），严格 `>=` 会差之毫厘地把高亮判给前一个分类。1px 容差可吸收浮点误差与真机像素对齐残差；分类间距有几百 px，不会造成误判。

### 完整交互流程

```
用户点击侧边栏"茶饮"
  → handleSidebarClick('section-tea')
    → activeCategory = 'section-tea'
    → 立目标锁 { id, top: 预计算的茶饮 top }
    → scrollIntoViewId = '' → nextTick → 'section-tea'
    → scroll-view 滚动到 #section-tea（期间 @scroll 被目标锁忽略）
    → 到达目标：scrollTop + 1px >= 目标 top → 解锁

用户手指滑商品列表（动画结束后 / 目标锁未释放时）
  → @touchstart → 解除目标锁
  → @scroll 事件触发 handleContentScroll
    → programmaticTarget 为 null → 正常执行
    → scrollTop = 350
    → 遍历预计算坐标：[咖啡:0, 茶饮:180, 星冰乐:360, ...]
    → 350 + 1 >= 180（命中茶饮）→ activeCategory = 'section-tea'
    → 侧边栏"茶饮"高亮
```

## 复盘（2026-10-06）：点击分类后高亮"回退一位"

### 现象

从第 1 个分类点第 9 个分类"茶瓦纳精选"：右侧滚动正常、落点精准，但左侧高亮先短暂显示"茶瓦纳精选"，随后回退到前一个分类"果昔奶昔"。且不稳定：同一操作约 1/3 概率正常；跨度更大的"早餐优选"（第 12 个）反而不复现。

### 排查方法

临时在 `use-products.ts` 加 `[linkage]` 日志（定位后已删除），记录：

- 点击目标与点击时的预算 top、`scroll-into-view` 赋值时刻、**固定 400ms 锁**的解锁时刻；
- **每一个** scroll 事件（包括被锁挡掉的）及其 `scrollTop`、按当前预算坐标会命中谁；
- 点击 1.2s 后用 `boundingClientRect` 实测真实位置对账：`trueScrollTop`（由 `.content-area` 与第一个分类的布局反推，不依赖 scroll 事件）、`targetResidualPx`（目标顶部相对滚动区顶部的偏移，0 = 恰好停住）、`scrollHeight` 等。

### 实测日志（模拟器；茶瓦纳 measuredTop = 6020.8，scrollHeight = 8347）

| 点击 | scroll 事件 | 400ms 解锁 | 事件是否生效 | 最终高亮 |
|---|---|---|---|---|
| 茶瓦纳 #1 | +484ms `scrollTop=6020.7998046875` | +433ms | 生效 → 严格比较失败 | ❌ 果昔奶昔 |
| 茶瓦纳 #2 | +454ms `scrollTop=6020.7998046875` | +424ms | 生效 → 严格比较失败 | ❌ 果昔奶昔 |
| 茶瓦纳 #3 | +412ms `scrollTop=6020.7998046875` | +430ms | 被锁挡掉 | ✅ 茶瓦纳 |
| 早餐优选 | +421ms `scrollTop=6708` | +421ms | 被锁挡掉（且 `6708 >= 6707.6` 本来也成立） | ✅ |
| 茶饮 | +425ms `scrollTop=1194.4000244140625` | +426ms | 被锁挡掉（且 `1194.40002 >= 1194` 本来也成立） | ✅ |

同时实测排除：落点精准（`targetResidualPx` = 0 / -0.4px）、预算坐标无漂移（`measuredTopVsTrueScrollTop` 与残差一致）、无尾部事件丢失（`lastEventVsTrue` = 0）。问题只出在**比较精度**与**解锁时机**。

### 根因 1（确定性）：float32 vs double 精度错配

Node 验证：

```js
Math.fround(6020.8) // 6020.7998046875    ← 向下偏
Math.fround(1194.4) // 1194.4000244140625 ← 向上偏

6020.7998046875 >= 6020.8 // false ← 差 0.0002px，命中失败
```

`scroll` 事件带出来的 `scrollTop` 是 **float32 精度**，而预算 top 是 **double**。是否回退取决于目标 top 的 float32 舍入方向——这解释了"茶瓦纳必现、早餐优选 / 茶饮从不出现"。

### 根因 2（随机性）：400ms 定时解锁与动画时长竞态

程序化滚动只在动画结束时发 1 个 scroll 事件（模拟器实测），时刻落在 click 后 +410~490ms；而锁在 nextTick 后 400ms 释放（click 后 +420~433ms）。事件早到就被锁挡掉（碰巧正确），晚到就执行了错误的严格比较。两者时间几乎相等，完全看几十毫秒抖动——这是"同一操作时对时错"的来源。

### 修复

1. **边界比较加 `BOUNDARY_TOLERANCE_PX = 1` 容差**：根治精度错配，同时让"到达判定"可靠。
2. **把 `isProgrammaticScroll + setTimeout(400)` 换成目标锁**：到达目标（±1px）或 `@touchstart` 才解锁，**不设超时**。根治竞态；真机上动画更慢、中间事件更多时，也不会出现"解锁后高亮跟着中间事件乱跳"。
3. **`@touchstart` 解锁是安全网，而非"打断动画"**：微信 scroll-view 的 `scroll-into-view` 平滑动画期间通常不接受拖拽，动画本身打不断；它的作用是当落点残差超容差、目标锁无法因"到达"而释放时，用户一碰列表即可恢复右→左联动，避免高亮被永久锁死。

### 设计取舍

- **为什么不用超时兜底**：超时后若再收到动画尾部的不完整事件，仍可能把高亮带偏；而"目标不可达"（例如真机落点残差大于容差）时保持点击项高亮本身就是合理交互，用户下一次触摸列表即自然校正。
- **为什么不用 IntersectionObserver**：它同样无法避免"程序化滚动期间 IO 回调也在触发"，仍需目标锁；同时引入异步回调、生命周期管理（数据渲染后重新 observe、卸载 `disconnect`）、uni-app 实例作用域等成本。它最大的优势（不依赖 scrollTop，规避浮点 / 节流）已被 1px 容差覆盖。当前数据量（16 分类、50 商品）下预算坐标足够稳定；若将来布局频繁变化或分类量级大增，再评估迁移。
